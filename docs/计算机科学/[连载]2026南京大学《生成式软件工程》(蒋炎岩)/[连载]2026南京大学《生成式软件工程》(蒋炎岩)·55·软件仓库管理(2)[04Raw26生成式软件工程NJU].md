## 正文

### 1. 课程作业说明与个人助手 lab 需求 / 布置实验的原因与下一个 lab 的关联 / readme 的 intent、项目文件构成与文件系统的历史局限

我们上周讲了一点版本管理，这周继续讲。我发布了一个作业，按照之前的说法，这门课所有的作业都是选做、自愿完成。最后肯定会验收，因为最终也许学校会让我们提交一个成绩。那么大家就会交一些链接，然后由我的机器人来给大家评分。我们的第一个lab算是一个比较时髦的需求，叫"会成长的个人助手"。对大家的要求都不限，你们想怎么做就怎么做，最好还是可以Vibe Code一个。而且我今天应该会在课上留时间，我自己就来Vibe Code一个，然后告诉大家：如果你直接让它Vibe Code的话，你会遇到什么样的小坑。

除了今天以外，下周——不对，不是下周，这周日要调休周二的课，所以这周日还有课——会讲软件的架构，会把它们连起来。这个例子的需求，你们每个同学都会需要，我自己也有，就是一个能够持续为你工作的个人助手。这些需求是供你参考的，当然如果你实现它的话，会有一点点成就感。比如你的学习数据库：你们这个学期可能会在上一些专业必修课，可能计算机网络或者概率统计之类比较困难的专业课，你可以把专业课的资料放进你的个人数据库；或者你参与了研究组的课题，你可以把研究组论文相关的文献、教科书整理成你的个人数据库。这是一种形式的数据库，不限。

你也可以把你自己的个人信息——我不知道大家是不是已经填表填得很烦了——每次填表都是给你一个doc表格，要填姓名、学号、身份证号，有时候还有个人简历这个那个。我现在已经把这些所有的事情都交给agent了。从以往到今年，有一个非常大的效率进步。我记得疫情的时候招过一个学生，研究生在我这里做了3年，做的是什么？自动填表系统，因为我们觉得填表很烦。等到他毕业的时候，突然有了ChatGPT，他很慌，觉得他做的事情马上就要被替代了。我说不要紧，你赶快答辩，然后就可以毕业了。这世界就是发展得这么快。

在个人数据库的基础上，你可以把数据库和你的email邮箱关联起来，如果有可能的话。比如我两周以后会在半夜给大家发邮件，然后你的agent可以把邮件回给我，就实现一个always on的后台。你们也许买一个很小的嵌入式小设备，一两百块钱，就可以在宿舍里持续跑你的agent loop。然后可以用你的信息办理教务系统的事务，就像我上课时候说的，这就是一句话，你直接一个像agent的调用就可以了。如果你们有兴趣，还可以做一个手机端的联动——也许是一个网页，也许是别的，甚至是一个苹果app或者Android app。你只要让agent去做，它会自己帮你下载好所有需要的东西，然后把你要的东西做出来。

然后为什么要布置这样的实验呢？看起来所有的任务都在AI的能力范围之内，但是如果你直接——我今天会试，我没试过——把这个实验要求直接让AI去做，它在最开始就会做出很多它认为看起来合理的决定，但这些决定会让项目的维护变得越来越困难，直到陷入焦油坑。所以我觉得每个同学都有必要体验一下软件工程里的焦油坑：当你的AI slop开始不断消耗你的token的时候，你终于会有一天下定决心——好，我要把这个项目删掉，从头重做，或者回退到某一个很早期的版本从头开始做。这是我们这个实验可能想要告诉大家的事情。当然我相信这个项目对每个同学来说都是有用的，这也是我设计实验的初衷。我提前预告一下。

我的下一个lab会和这个lab有非常大的关联，而且你们暂时猜不到。你会发现，你现在lab1的实验要求都做好了，它成为一个非常舒适的个人助手，然后我再给你加一个需求，这个需求和前面所有的都有关联、并且有一定的冲突，然后你一点一点去改，越改越崩溃、越改越崩溃，就有这样一个体验。所以大家可以期待一下后面的lab。所以如果你不做，比如你现在lab1选择躺倒，或者就不管它让AI直接做，下一次再把这个直接删掉，那可能就没有这个软件工程的体验了。这是我想做这个lab的原因。

好，我们回顾一下上节课讲的软件项目管理。项目是各种文件的集合：你的intent、一些设计文档、你的readme都在项目里。其实我不喜欢AI写出来的那种非常非常长的readme。对我来说，readme应该就写一下你设计这个项目的最初初衷——你想做一个什么样的产品，这个产品能达到什么样的效果，可能配两张screenshots，以及你最重要的那些设计。什么感觉呢？有一天你突然想了一个非常好的点子，真的想用它挣一个亿。要挣一个亿的时候，你要组建一个创业团队，你要说服你计算机科学圈子里面的人，比如你要说服我出来干。其实你只需要一个比较短的readme，这是你的intent：你想做这个东西。剩下比如我有架构能力、有写代码能力，我可以把剩下的东西给你补出来。你不需要知道这个软件系统的specification是什么、用什么数据库、怎么支持用户从1到10到100到100万到1亿——这个你可能没有计算机科学的知识，但你不需要有，你只要有那个最原始的设计，那个intent。

然后再到spec，就有我刚才说的：我要选什么样的数据库，甚至选什么样的编程语言，我的项目结构是什么等等。各种各样的，小到每个模块的接口都属于spec。然后再到code implementation，它现在都在这个项目里。有了这样的项目以后，很自然地你就需要一个容器，把这些各种各样的文件管理起来。我们说大家用文件系统来管理项目，其实真的就是图方便：你回到1950年、1960年的时候，操作系统给你的存储功能就只有文件，没有别的，那个时候关系型数据库还没发明出来，所以所有的程序员别无他法，只能把项目以文件的形式存进来。这更多时候是一个历史原因，历史不停往后涨导致的。我自己觉得文件系统可能不是组织项目的正确方式，因为文件系统其实丢失了很多不适合用文件表达的信息。有些信息其实是比较容易表达的，比如intent、spec——一条文档，说明这个地方我是怎么想的，或者这个测试用例是什么、输入是什么、输出是什么，然后我要assert程序运行过程中什么东西不能被违反。

### 2. 文档与代码不一致导致技术债与 Software Traceability 问题 / Git 理念与让 AI 维护 artifacts 一致性、生成相关 view

但是你马上会发现，项目里面有很多隐藏的关联是没有的。举个例子，你经常会在AI写代码的时候——现在agent会稍微好一点，有时候也不会——你让它把某个实现方法改掉，比如你要把linked list换成更高效的tree结构去优化性能，这是很常见的：突然发现性能不够了，让AI去改，AI啪啪啪就把代码改了。但你可能没想到，你在某一个markdown文档里写过"我这个项目是用linked list管理数据的"。

在项目当中，你的文档、代码和测试之间其实形成了一个关联。你写文档的时候可能还没有代码，所以你先写了那个文档，随手一写"这是个linked list"。但一旦代码实现了这个关联，又没有强行跟文档联系起来，这就是一个技术债，technical debt。因为以后文档和代码不断向前推演，它们的不一致只会越来越多、不会越来越少，这个软件就陷入维护的泥潭了。因为后面你拿出一份代码，甚至AI拿出一份代码，到底是文档说的对还是代码说的对？你跟AI聊天的历史没有了——那个chat已经消失了，你换了一台电脑。你的git repo里可能还有一些change日志，但到最后你真的就不知道到底是代码对还是文档对。

其实在软件工程里，这是一个研究了非常非常长时间的问题，叫traceability。你看，这是2014年的一篇综述，review了更早的文章，就叫software traceability，可追踪性。所谓追踪，就是我们发现文件只是图方便保存在文件系统里；那么一个软件项目里各种各样的测试用例、文档，哪怕文档中间的一行代码，它们之间的关联是什么？我们能不能在软件系统的演进过程中仍然维持它？这其实是一个非常软件工程的问题。所以很多时候我们觉得蛮有意思的：文件系统将错就错，大家总有一天会发现，用文件系统管理代码你受不了了——打压缩包发布，打压缩包发给合作者——这件事情已经维护不下去了。所以就有了SVN、有了Git。那下一个是什么？大家有没有想过。

我今天一会会讲Jujutsu（jj），另外一个可能甚至比Git还要好用一点的版本控制工具。但我也觉得，刚才说到traceability，如果以后我们再也都不写代码了，那软件就不应该像现在这样在git repo里面管理——我们有好多文件，什么readme.md，什么hello.c，还有一个docs下的什么文档。如果所有的这些东西我们人都不管了，我们有没有可能……我一直在想，等这个未来到来，我们把软件或者说部件之间——也许我们还是需要文档，但我们的文档可能是好多个切片，把这些切片变成好多的object或者entity。然后这个文档和实现之间就有一个关系：这个代码实现了这个文档；我可能有个测试用例，这个测试用例也关联着文档，文档和测试用例关联起来，测试用例和代码的这部分实现关联起来，这个文档又和那个文档关联起来。你看，这是一个完全结构化的东西，没有办法在文件系统里以一个树状的形式表达——这是一个随便连接的、有cycle的图。这个东西我可以把它放到一个数据库里，叫repo.db。显然人类没有办法用现在UNIX世界里的工具去维护这样的repository了。但不要紧，我们应该怎么解决呢？用魔法打败魔法：人类理解不了的东西，我们只要训练AI——只要有强化学习的反馈信号，我们就可以训练AI去理解这个repo。所以我们要干的是什么呢？这是一个非常大的项目——Linux内核数据库，或者你们想做的价值一个亿的产品。每次你就说"好，AI"，因为你也不太可能一下子说"我要把这个产品直接变成另外一个产品"。

当这个软件系统已经在工作了，你一般来说就是要给它增加一个功能、修改一个功能。然后这跟Git的理念、philosophy很像：Git管理了文件目录、快照和快照之间的关系。Git希望我们能够小步前进：我每做一件事——fix一个bug、改一个文档——都产生一个commit，这样就可以在多人之间协作，每个人产生自己的commit，然后我们用rebase、merge，或者fast-forward这种，或者普通的merge，来创建一个可追踪的整个项目的修改历史。

那如果我们以后也不要文件，也许还是可以用文件系统来管理，但我们要的是：可以让AI自动维护所有软件artifacts之间的一致性。代码和文档必须一致：我文档说这是linked list，我的实现里必须是linked list；我的test case测试用例，文档里说要有ABC三个方面的测试，那test case就必须有ABC，它们都是关联起来的。

然后你想，在Git里我们希望小步前进。同样的，当我们谈要做一小步的时候，我们知道这一小步是干什么的，所以你可以跟AI chat：说"我现在发现它有个bug"，或者"我做了一个产品，比如我今天对这个幻灯片样式不满意"，这其实就是一个小步。这时候，一个大型软件系统里绝大部分内容跟这个小步都是没有关系的。比如我说我对幻灯片的样式不满意，大家可以直接看我的repo，看顶层的结构：我有一些assets，甚至还有.cache缓存目录，然后有P1、P2、P3、P4、P5，还有一些脚本等等。

任何一个软件系统，当你只做一小步的时候，你只需要看到这个软件系统的一小部分，大部分东西应该是无关的。既然是无关的，我们就可以让AI根据我们的chat，把和我相关的东西摘出来。它可以知道：我现在需要的是这个文件、这个test case和这个文档，其他都不需要了。然后你想AI有什么能力？AI有动态生成任何内容的能力——everything is code，content as code，code可以表达任何东西。所以AI可以根据我的chat，生成一个和我要改的这一小步相关的view，一个视图。你们学到的各种系统里的概念还是有用的：不是所有同学都学过数据库，数据库里有一个叫view的概念：数据就在那里，但我可以创建一个不一样的查询，把它以另一个形式展示出来。这就是这个很简单的想法：我希望把这些数据以另外一个形式展现出来。

比如当我看到的时候，我看到的不是这些代码、文档、文件，而是一个可视化的看板，看板上面列出了和我这一小步相关的东西，然后问我要改什么。我一把改完以后，同样还是从一个view到另一个view，它还是同一个repo.db，但这一小步就会把相关联的东西都改了——比如我要增加一种类型的测试用例，它就会在这些地方加一些测试用例，有些地方可能要改掉——它就从一种一致的状态，在各种错综复杂的关系里，做一次小步的修改到下一个版本。这样软件工程就又彻底变了。我觉得这是未来有可能发生的：在AI内部，它是这样生产软件的。

### 3. 未来不看代码、经典课程价值与 contributing.md、rebase 规则 / Git 快照、merge 的 ownership 问题与 rebase 的冲突风险 / change 作为 first class citizen 与 Jujutsu 取消 staging area

从此以后我们也就再也不要看代码了。我觉得你们看到现在的这种现代IDE，比如Cursor，我其实还蛮讨厌的。它现在打开默认就是agent mode，原来那个我们熟悉的IDE就没有了，强迫你用类似于chat的方式跟它沟通。但因为我还是比较精通古法编程的，有时候还是对代码有一些掌控欲——可能是不好的，可能是不对的。但未来可能会是这样，这可能是一个途径。

同学们肯定也会焦虑：如果未来这件事情真的有可能发生，而且可能一两年以后就有一个公司把这东西做出来了，那我们学那么多东西还怎么办？其实你发现，在我们思考、创造这些东西的过程当中，用的都是你们学过的这些经典的、集大成的computer science课程。我刚才说的数据库里的视图，我借用了数据库的概念——实体和关系；然后我借用了git——这个模型没有变：git长期的开发经验说我们要一步一步向前。如果在这个模型底下我们是大步向前呢？那就惨了。当然也有可能发生：模型非常非常强，一个非常大型的项目一步啪就变成下一个了，这个怎么做我们现在还不知道。但至少在初期，我们可能还是要沿用过去的、大家积累的软件工程智慧去小步向前，通往那个极乐的世界。但我还是相信那个极乐世界确实有可能能到。

这就引发了一个我觉得在大学里蛮有意思的评论。这个同学应该已经毕业了。上节课我问同学们git rebase，大家都不知道什么是git rebase。然后他raise了一个valid point：他说学生时代大多数人是不会和他人共同合作的，就是做作业，所以rebase、merge用得就很少。正确，这个point是对的，你们做作业的时候确实不会。我的回应大概是这样的：但是如果你真的去外面的世界走一走，这个互联网开发者社区铺天盖地都是文档，所以你总有一天会留意别人的项目，会看到叫contributing.md的东西。

然后一般这个commit——你们有没有同学问过rebase？没关系，错了就错了，我没有。它还是仓库根目录下的一份贡献者指南，通常回答"我怎么参与这个项目"。你看它里面就有项目的总体结构、分支、提交信息、PR的规范和流程。如果你看过很多项目的contributing.md，随手打开看一眼，发现里面东西都知道了，那你就知道了；如果你不知道——比如有一天你一定会看到一个项目里说"你必须要在自己的分支上rebase，禁止直接创建分叉的merge"——你就会知道rebase是干什么的。

现在的社会变得太快了。有一种学生——不是批评——是因为你们上高中的时候就是这样：老师不教的就是你不需要会的，考试不考就是你不用学的。为了升学利益最大化，这个是正确的，没有错。但到大学以后，如果你们还带着这个思维，就会有这样一个gap——新人类和旧人类之间的gap。当然我相信每一个同学还是可以成为新人类的，你只需要有一些注意力，去注意到更多的东西。因为我有一个危机感：AI时代的斩杀线以下的价值就全部归零。当然我觉得现在斩杀线可能还斩不到各位985高校computer science专业的同学。

但可能那些低级智力劳动，比如会计从业者——好像我看过一个报道，中国可能有1000万还是多少会计从业者。这个行业顶端的人暂时肯定没有威胁，但底下的大量的人都面临被agent替代斩杀的危险。所以你们需要在那些经典的课程上——不管是操作系统、编译器这些，还是软件工程——学到一些软件工程的智慧、经典的东西，最终形成你们自己的理解。这是一些评论和复习。

好，那我们继续回到软件工程。不管是畅想未来会发生什么，还是我们回到Git：Git管理的是快照，也就是一个目录——整个项目的一个快照。我可以在快照上做开发，开发要求小步。现在有一两个开发者，一个A、一个B，可以独立地在这两个分支上做开发。这个东西是commit。如果你想把它合起来，在Git原始的模型里，rebase相对来说不那么提倡使用：它说好，你会创建一个两路的merge，它有两个parent，继承了这两个分支的修改。

但这会带来一些问题。比如merge是由A来干的，那merge里面由B写的那些内容，作者就变成A了——它有一个隐藏的作者修改。比如B在这儿加了一行，这个可能还能追溯到B；但如果发生冲突，在resolve的时候，冲突解决完以后这个提交就是由A完成的，那B改的代码，ownership最后又归到了A。所以这会带来一些相对来说有点小麻烦的问题。然后rebase解决了这个问题。rebase——我还是横过来画，第一排的同学是不是有点看不到？

如果我现在有两个历史：A同学改了两次，做了两次提交，得到两个快照，delta一、delta二；然后这个时候另外一个同学开始改。rebase做了一件什么事呢？比如说A先改了文档，然后又加了测试；B加了一个feature，然后又加了一个测试。那rebase不是直接把它们两个合成一个、把两条线路并起来的提交，而是我试图先试试：这个feature能不能加在A的后面？如果加上了，OK那就成功了。

但是这里有一个很大的风险：我可能在这个里面加入了一个测试用例，而这个测试用例和这个feature不兼容，这是有可能的；或者甚至他们改了同一个地方，做了两个完全不兼容的东西，那这时候它是有可能失败的。如果成功，那就比较好：我再把test放过来，如果也成功，那就一路相当于——如果这两条线上的修改完全没有任何冲突，我就可以一路合并过去，变成一个线性的历史。

但是一旦发生冲突，这是非常危险的。为什么？一旦冲突，你就需要resolve，你会进入一个rebase的模式。你们如果进入过这个模式，会发现瞬间自己就不知道应该怎么办了。这时候你打开agent说："哎，我发生了什么？"agent会细心地解释给你。更麻烦的是，你就算是把这个feature搬过来了，搬test的时候可能又失败，你还需要再把test搬过来，而且每一次你都会创建一个新的提交。每一个commit都有id。如果你是一个两路的merge，所有的id都保留了，你会创建一个新的id；但因为你是rebase，每次rebase就会创建一个新的commit——这个快照的base本来在这，rebase要把base改到这里来——你就会创建一个新的id，历史就变了。然后你会感觉到这里有一点点轻微的不一致，觉得好像不是完全想这样来管理软件。

因为我们关心的是修改：我希望的是把这个修改搬过来、把那个修改搬过来。在Git里面，修改是用commit来替代的——我现在有一个commit，这个commit和它的parent之间的关系就叫一个修改。它没有一个专门的叫change的对象，所以用commit来代替修改。绝大部分情况下这样还能满足，但如果我们把change也变成first class citizen，会发生什么呢？你就发明了下一代更好用的版本控制系统。比如jj（Jujutsu），它是和git底层完全兼容的，你可以直接把它当git用，但它增加了一个叫做change的概念：每一个change都有独立的id，它可以把好多change——比如rebase的时候，直接把change搬过来。

change还是有可能冲突的，冲突是解决不了的。如果我在rebase的时候冲突，这是解决不了的。但是因为它有这个change object、change这个概念，所以它可以把这些change一路带下来，直接rebase到这里，虽然里面引入了好多冲突。它还是运用了git的冲突记录，但它有一套自己的记录方式，把所有change的冲突都塞进去，然后你可以在这里把它们搬过来，再在这里resolve。它的底层模型没有变，但用起来会舒服很多。

它还有一个很好的特点：不需要staging area。在git里面你最讨厌的是什么呢？我上操作系统课的时候会讲这个例子：你现在有个repo，改了一个文件，比如hello.c，改改改改到一半，这个时候项目还不能编译、不能运行、测试也通不过。突然导师给你打电话："哎呀，我这边有个很高很高优先级的项目，有个bug，马上客户那边就要交不了差了，赶快把这个bug一分钟给我修了。"那你怎么办？

你不应该commit，你需要的是把它加到index里，然后git stash，git stash会把工作区压栈保存。这其实是一个比较讨厌的操作：stash一个东西，然后你去修原来那个bug；刚修了一半，导师又打电话："哎呀这个bug别修了，我还有一个优先级更高的bug，你去修。"你又要再stash一次。git stash是一个栈，里面会有好多个提交，你需要去管理那个栈。

如果你想象，你随时随地都在编辑这个repo，这不就是一个change吗？你现在把hello.c改一改，加一行减一行，这都是change。所以Jujutsu好像在做一件什么事呢？好像是你但凡改了一个字节，它都会立即做一个git commit。当然这个commit不会产生好多线性历史，而是先把上一次的那个提交抹掉——你改了一个字节，上一次的提交就被抹掉了——然后重新用当前这个修改去替代这个提交。也就是说，因为现在有个change、有个当前的snapshot，它永远是处于一个提交的状态、一个change提交的状态。那你就很舒服了，连staging area也不需要了。这是一个非常好的东西。

### 4. 从 change 出发重新设计版本管理系统：Agent 时代的改进需求

你从"把change作为first class citizen"开始，再往后推，就可以发明自己的版本管理系统。当然这不是它的全部，它还有一些别的路线可以推导出来。你们适当的时候可以质疑一下：Git有没有哪里做得不够好？如果可以做得更好，还能做怎样的设计？我觉得这是非常有趣的设计，你们可以在agent的带领下——或者说我开了一个头，给你们一些motivation——把最重要的prompt交给agent，说"我如果要学Jujutsu，我想从change开始理解"。

如果你看它的tutorial，它一上来就会告诉你：它没有staging area等等。你管理版本更自然、对人类更友好，实际上它可能对agent也稍微更友好一点。所以我觉得这就是为什么你们作为AI native的人类，能够淘汰掉我们这一代人：我已经形成了Git的肌肉记忆，而比我更老的一代人，已经形成了SVN的肌肉记忆。一旦人形成一个肌肉记忆，要把这个习惯掰过来就很困难了。比如我现在对Git有肌肉记忆，即便能够理解Jujutsu的概念，甚至理解得比你们这些初学者还要更好一些——我可以从first principle去思考它，相当于virtually reimplement这个系统——但我即便能够理解，也没有足够的时间再去训练另外一个肌肉记忆。

所以你们是反过来的：你们应该趁现在还没有形成记忆的时候，直接去用那个对的东西。人类历史都是这样积累的：SVN实在用不下去了才用Git；Git发现了缺点以后有了Jujutsu。所以你们可以先记住一个最正确的设计，然后再去理解这个设计。你再回头想的时候——原来Git这么蠢。在Git出现的时候，大家会觉得Git这么先进：它是一个persistent data structure，而SVN从一开始、从纯delta那条线就走错了。到如今你再回头看，原来Git也犯了一些设计上的问题——当然是因为它最早的时候没有想过rebase会有这么大的impact，它有merge就已经很好了，就能解决手上的问题了，所以它可能没有把这个概念模型想得更清楚。

这是一些有意思的comments，也是学习时的一些建议。你们在学东西的时候，尤其在AI的辅助下，可以不断地往前走。这门课不是软件工程，这门课是生成式软件工程，所以我们要真正做的事是：在agent的时代，再次重新设计版本管理系统。

也就是说，你当然可以让agent去用Git，也可以让agent去用Jujutsu。Jujutsu对人类来说是一个很大的进步，但对agent来说进步可能相对小一些，因为它好像很会rebase这些。你看我们一路走过来：SVN有局限，Git有局限。那么在agent的时代，我们的局限是什么、要打破和改进的又是什么？

刚才所有的version control system都有一个假设：这个version control system的使用者是人类。人类有什么特点呢？人类是single thread的生物。我一直上操作系统课讲并发程序，并发程序我打什么比方呢？你把线程想象成一个人：你的线程可以访问共享内存，访问共享内存时两个基本操作是load和store，或者说read和write。我可以从一个变量里读一个值，把X读到临时变量里；或者写X等于一。这两个操作不能同时进行——既读一个又写一个，就需要一个原子指令了。

然后绝大部分shared memory access，你能想象成人是什么呢？我如果想要观察这个世界，那对不起，我的手要抱在后面，我只能看。等我看完了——比如我看到这个同学在这——我想要对他施加一个效果，想用粉笔导弹射击他，当我想要真正write、写一个变量的时候，我必须把眼睛闭起来。而我把眼睛闭起来扔的时候，注意我读到的那个值其实已经失效了，是旧的值——我上一个时刻读的。在上一个时刻到这个时刻之间可能经历了很多事情：可能我被换下CPU了，被中断打断了，换了另外一个线程上来执行，可能执行了一秒钟以后我才恢复过来。我恢复过来以后，看到寄存器里面那个X值——上次读X等于一——然后我就把粉笔扔出去了，那很有可能扔的就是错的。这就是single thread。

多线程共享内存带来了无穷的问题。其实人类也是这样的：人和人之间有无法逾越的物理屏障，你不能理解我的思想，我也不能理解你的思想。我是一个独立的个体，由分子把我很强地连在一起。OK，我们只有一份设备——一双手、一张嘴、一对眼睛。我们编辑代码库、以这种方式产生change，就是以小时为单位的。一个软件公司，负责一个模块的开发可能多也就十几个人——十几个人已经是不小的团队了。十几个人每个人以小时为单位开发，最多也就是以10分钟这样的单位产生一个提交。

以10分钟为单位产生提交，意味着这个速度会比人和人之间沟通的速度慢很多。尤其是一个team，工位都在一起——你们研究生的工位都在一起——你要写一个东西要一两个小时，写之前你肯定跟师兄说一声："哎，师兄，我要干个这个，行不行？"十秒二十秒三十秒，师兄说"行，你去改吧，我们现在不改"。或者你们去厂里打工，厂里每天早上都要开会，每天早上的leader都会把任务分出来：今天要干什么，你做什么、你做什么、你做什么。你提前在半小时的时间里就划分了一个scope，把项目切开了，领了其中一部分走，然后去产生提交。当然这是古法编程。在古法编程的时代，你就看到stash是一个合理的设计：刚才说的"你导师给你打电话"是可能发生的，但"你修到一半导师再给你打电话"是不太可能发生的，发生概率很低。绝大部分时候你的stash里就一层。如果有好多层，管理起来挺麻烦的，你还需要rebase stash，所以你会尽可能保证stash不要太深。因为你可以拒绝一个工作，或者说"我手上有一个更高优先级的工作，对不起，我不能干这个"，等干完了以后你自己可以排一个队列。所以git是给人用的。

但是在agent的时代，这件事情变了。如果是一个agent team，单个agent生产AI slop的速度就远远快于人——它生成AI slop以分钟级为单位，甚至更快。有时候你让它fix一个东西，上下文热的时候可能就几十秒钟；DeepSeek V4 Flash干活的时候几秒钟就做了。当agent以秒级工作时，可以以秒级产生一个原子提交，并且你可以轻易得到一个十倍一百倍的agent team的时候，git或者jj——jj举起来是跟git兼容的——这样一个为人设计的模型，就有点跟不上了，确实是有一点跟不上这个速度。

就算是大型项目有一些门控——我改完这个部分以后必须经过一个测试流水线，这个测试可能本身就要运行几分钟，可以放缓agent提交的速度——但毫无疑问，agent加速了软件开发的过程。如果agent加速了软件开发的过程，我们应该怎样为agent设计版本管理的系统呢？

### 5. 多 Agent 协作、Git worktree 与沟通成本导致团队无法变大

首先我们可以让agent沿用人的模型。每个agent都有自己的开发计算机，那你就把single thread的人类和agent做一个严格一一对应的类比：让它有一台独立的电脑，可能是个容器，把它放到git仓库上，然后直接instruct agent："好，我的remote仓库在git上，你现在是一个单人开发者，你可以从tmux里面收到命令，收到命令就可以开干。"所以这件事情其实非常容易实现。

比如我之前那个项目，我可以这样做。然后agent时代有点什么好呢？每个人都是领导，你就是总指挥。现在有两个tmux session——在实际开发的时候，这两个tmux session位于两台不同的机器或者不同的容器，物理上隔离开的，它看不到世界上其他的人。还故意用一个可能在中国现在还能用的词：Master。然后我现在就是master，你看这个名字改过来了：Slave。好，我可以给它们每一个都起个名字，比如Pi、Coding Agent。

那我可以让它干什么呢？OK，Anyway，it doesn't matter。你看它们两个就开始工作了。当AI agent变快的时候，你想想，如果你的指挥发生一点点差错，或者哪怕指挥得没问题——现在一个流行的paradigm是：你有一个监工的agent，然后有好多个子agent。有些团队为了最大化模型的智力、防止AI生成你不想要的东西，会放两个比较强的模型，比如由Codex来设计、让Claude来review，让它们互相打架、达成一致。你只要开两个tmux就行了，你的主agent负责协调，观看它们的输出或总结报告，然后往里面inject prompt。

然后这个多agent就转起来了。我看一下report status，然后你发现：如果大家工作在同一个git仓库上，就会有一些麻烦；但如果他们工作在不同的repo上，就完全可以——他们可以去远端拉取别人的提交，冲突了自己修复，在必要的时候还可以给master agent发消息。你们立即就可以构建出这样一个多agent系统。

今天我们也有一些work around，比如git就有worktree这样的功能。所以你看我可以问它："我的老师说git worktree可以改进这种并行的工作方式，那么能不能让这两个tmux session都工作在worktree上？"其实提问是关键。你们可以在各种信息里看到——比如你早上走到教室，看微信公众号，公众号上说到了git worktree，或者提到了什么sandbox container——你就可以立即让agent帮你试一试，然后看看它在做什么。这不是一个比较容易的任务吗？OK，它确实在写脚本，你看它把编辑器退出来了，应该OK了。git worktree允许我们创建一个工作树，这个工作树连接到一个remote、一个git repo，然后我可以在里面做独立的提交，在一个隔离的环境里做独立的提交。

大家都知道.git是一个目录：比如说我现在这个仓库，.git里面有一些东西，比如logs，还有objects——三种类型的对象。那worktree里面的.git是什么呢？点开就是一个普通的文件，是一个文本文件。如果你继续追问agent，agent会告诉你——这个我也是才知道的——除了.git是目录以外，它还可以是这样一个特定格式的文件：这个文件里写着gitdir，指向了一个worktree，而这只是文件系统里面的一个文件。所以你看到，Git最大程度上复用了操作系统里面的机制。这个worktree是一个小型的git目录，它依然有HEAD、index、locks这些，是一个微型的git目录，但它是依附于原有的那个git目录而生的。这个特性在AI时代突然间变得有点有用了。

我们可以在本地提交，直接在本地互相可见，不需要互相pull和push。如果你像刚才说的，开了好几台虚拟机，每台虚拟机里放一个agent，直接往tmux里注入命令，当然可以，完全可以完成。但是worktree提供了一个更轻量的合作方式。如果有冲突的修改，它仍然需要merge和rebase才能合并，这样性能会更高一点。那我们回到这个agent team：如果我们有agent team或者agent swarm，除了今天worktree这样的机制以外，还要回头想——为什么我们需要版本控制？因为我们人类的限制——刚才说的10分钟，哪怕是一个小团队也要10分钟产生一个commit——是人的限制塑造了这个工具：人之间的communication。

communication导致你每天早上都要开一次会，同步各人的进展，再把任务分下去。而且就算是人做了这样的沟通，你也知道：有时候你室友向你请教一个数学问题，明明你会做，就是怎么都没办法给他讲明白——除非你是一个很好的老师，能够共情别人、站在别人的角度思考。沟通的成本就是很高的。这也是为什么大厂和小厂——尤其是初创公司、初创团队——效率可以更高：当软件系统大了、人多了以后，沟通的效率变低了，产出的速度也就降下来了。所以一个100人的团队，不可能达到一个10人团队效率的十倍，可能有两倍、三倍就已经挺不错了。所以团队没有办法变大。

所以我们需要git各种各样的best practice：快照、小步前进。你改一个title也要做一个commit，做一个小事也要做一个commit，这些小的commit每个都可以追溯。因为一旦出问题，你需要回溯到那个人做事commit的那个时间，而那个人是有记忆的：开发者会回想起来，那天我们早上开了一个会，我收到要做这个需求，做这个需求的时候沟通发生了一个问题——大家找到那个时间的沟通记录文档，再说这个地方应该怎么修正。所以你看有git bisect、git blame这些专门为人设计的特性。但你想一想，如果是由agent team或者agent swarm来实现你的项目，我们还需要git blame吗？

人可以blame：你事情做不好，我blame你多了，你就该被开掉了，实习生你就背锅了。但如果agent没有"被开除"这样的概念的时候，这个模型就变了，我们再也不需要blame了。我们的项目只要前进就可以了。前进的时候，有时候也不需要知道到底是哪一个提交引入了这个错误——我只要知道这个地方错了，也不用管它历史上是怎么造成的，把这个错误修了就行了。因为agent之间的communication——而且尤其现在更好玩的是，我们的每个agent都是相同的模型，是完全相同的克隆体。同一个事情让它们来做，虽然模型还有不确定性，但它们大概率会收敛到相同的结果——同样的prompt做同一件事可能有点细微的差别，但最终方向性的东西会收敛到相同的结果。所以我们再也不要blame了。

那我们的项目就永远是一个向前进的过程。快照肯定还是需要的：比如这个方向走错了，你如果没有保留历史上某一个snapshot，一下子往前走好多以后再回去，代价可能比你一点一点往前修还要大。所以保留快照肯定还是需要的。那我们就是不断地大步向前，几乎永远不要看过去——git的提交历史里只是留了一些lessons，记录了项目到底经历了什么样的演化。然后不停往前走、往前走，合并、合并、合并。所以历史的价值可以从"谁写错了"变成"我怎么把它修好"，只要能知道从现在开始怎么样往前进就可以了。

### 6. 数据库并发控制类比：乐观与悲观并发控制在 Agent 时代的取舍

所以你再想想，这个时候你在计算机科学学到的那些知识又起作用了。我又回到讲操作系统的时候、讲并发的时候。数据库——现在的这个git模型更像是数据库里面的并发控制。比如说有两条SQL，每条SQL都是一个transaction，一个很大的transaction，中间可以混任何代码。你可以先select——你先读一下；我这边也可以select，读完以后可以做代码的计算，比如Python或JavaScript代码——这个代码是图灵完备的，你永远不知道它会根据我看到的结果算出什么。我甚至也可以从外面，比如根据我当前的时间再算一个什么东西，算完以后再update。

Update的时候就会产生冲突，也可能产生死锁。这个update要读它，那个update要读它，就会产生一个循环依赖——可能是数据的依赖，也可能是"我要锁你、你要锁我"的对象依赖，产生死锁。然后这会导致这个transaction的abort：这个transaction说"对不起，这个我不能进行了，我检测到一个循环依赖，我要回滚"，相当于roll back。

其实git的模型有一点像乐观的并发控制（optimistic）。为什么是乐观的呢？它假设这两个transaction不会冲突，执行的时候就假设它们不会冲突。这个假设在数据库系统当中是大概率成立的，为什么呢？想想教务系统：你们每个同学读的都是自己的数据、写的也都是自己的数据——我选课选的是我的课，查看课表查看的是我的课表，所以全局冲突不太可能。两个同学哪怕同时开始选课，我读我的、写我的，这两个就可以过去。Git也是一样：假设这样开发——我们已经事先开过会了，今天早上开过会了——我顺着这条路先做这个，另一个人做那个，合并的时候大概率不会产生冲突，不管是merge也好、rebase也好，都能顺利完成。

但是这是古法编程时代的。如果agent快了1000倍，主agent又没有协调好，一下子就分了好多任务出去，它们就真的会更频繁地触发transaction的abort。这种abort在AI时代也不是什么大问题：agent反正出错了、出了conflict，它修，它能修好。但是不是我们在agent的时代可以换一种并发控制的方式？

你想想操作系统里面学到的并发控制——你们用什么做并发控制？上锁。锁和数据库里的transaction有点不一样：你是lock一个东西。我上课经常说"一把大锁保平安"，做实验你们就知道了：当我想要访问可能冲突的资源的时候，我会先把它锁住——"我先抓了一把锁"——这把锁一旦抓上，别人想要再lock的时候，对不起，后来者必须等到前面的锁release，必须是一个先来后到建立起来的关系，而不是这种optimistic的"大家先往前跑、跑了再说"。我必须在使用这个资源之前，declare对这个资源的使用，用上锁的方式。

所以你看，只有你在操作系统课、数据库课真的把这些东西学会了，回来想的时候——软件工程里这些概念又再做了一次。所以想想现在如果agent动作非常快，我们其实应该用更加偏向悲观的并发控制：也就是说我今天要做什么事，或者我有个主agent，我规划，规划完了以后立马把这个项目的某一个部分锁上。我可以让git——应该在一个git repo——支持一个锁的操作，把scope说好："我现在锁住了，我要做一件事，需要先上锁，上锁以后做完commit；另外一边也可以上锁，但如果它想干的事情被另外一个人锁上了，它就必须等前面的人释放，才能再上锁。"这样不就几乎避免了所有的冲突吗？比如我可以在文件级上锁，避免两个agent同时写同一个测试、往同一个测试或者一个配置里面做更改。又因为agent数量足够多、速度足够快，我还是可以保证整体项目进度往前推——也许还有别的agent可以继续运行。

这也就跟操作系统里写并发程序一样：如果你一把大锁保平安了，或者哪怕你把锁拆细成互斥锁——互斥锁的本质是不要并行、不要并发，它和多处理器并行是有根本矛盾的，它把一个能并发的程序退回成一个串行程序。但是当这个系统里有好多独立的、不冲突的线程在运行的时候，我即便每一个线程都持有了一把锁，它还是可以高效运行。即便悲观，依然可以是高效的。这些知识关联起来让你看清楚：我觉得在agent的时代，我们又可以重新设计一个版本控制的系统。在agent时代，软件工程肯定要发生很大的变化。从first principle出发——我们要管理快照、管理版本、管理change，还要管理飞快的change——那答案是什么？可能git是一条线；如果我们用一种像这样的方式来管理软件，那可能又是另外一条线。

### 7. 操作系统与数据库学习的价值、团队管理与单向汉诺塔题目

所以你发现学操作系统、学数据库这些东西有用。虽然你痛苦，你怀疑在AI时代学这种东西——AI都会写数据库了，SQL查询我早就早就不写了。那我们还有没有可能学数据库是有用的？答案是有用的，你还是去好好学习。数据库里也有advisory lock这样的机制。也是为什么我喜欢上课的原因：如果我不来上操作系统课、不上这个生成式软件工程课，可能就不会让我在备课的时候把这些事情在脑袋里再过一遍——是不是地球上所有人都错了。因为我要讲给你们的时候，我必须要共情我的听众，考虑到你们是只能接受平实朴实逻辑的听众，不能直接就说"哎，操作系统是怎么设计的"等等，我必须把最顶层的idea提炼出来，试图让大家共情。当然可能我做得也不够好，你们可以在AI的帮助下重新理解一下。

OK好，版本控制、版本管理，基本上我就讲完了：从历史动机，到过去的git，到现在这次讲到的未来可能发生的事情。但是版本控制本质上还是一个工具——不管是不是我刚才说的那种基于乐观或者悲观锁的版本控制——真正困难的是进度，是团队的管理。我们为什么现在还需要软件工程？就是因为我们现在没有办法做到一句话直接出一个高质量的产品。如果斩杀线到了，老板有一个想法就说"我要做一个agent用的微信"——我随口一说，或者说做一个AI时代的微信，这个微信是社交爆款，以后这些人社交可能也不用微信了，用我的。当然你可能有个更具体的想法。如果AI直接就能出那个微信级的产品，那软件工程就已经死了，我们就都死了。但是斩杀线暂时还没有到，至少还没有到团队管理这一层面。所以我们可能还要学。但也许有一天我真的也要被拆掉——因为摩尔定律本质上也是一个scaling law，它现在还是成立的。

模型肯定会更强、更小、更快，也许算力有一天能够唤出我们的智能。但今天至少AI还不知道怎么做团队的管理，因为每当你多一个人的时候，沟通的关系都是平方级上升的。因此现在软件工程团队里最难招的其实不是码农，是那个能把任务分解的team leader——最难招的是那种能把国民级的应用分解的人。他说"我要造一个微信"，他能把微信分出来：一个100人的团队，分出十个小团队，十个人十个team leader干，最后加起来拼起来还能成为一个团队——这个人最稀缺。然后接下来能够带领小团队的人其实也很稀缺。《人月神话》里就是人与人之间平方级的沟通关系：就算你能把份内的事情做好，因为这个平方级的沟通关系——别人也在做他的事，你不百分之百知道别人在做什么，或者你对整体的团队了解不是很好——你最后还是会有各种冲突，你写的测试我过不了，就经常会发生这样的事情。

如果我们想要管一个团队的话，或者说你们希望在毕业的时候具备一定的团队管理能力，你现在就可以把自己当成那个主agent，就像我刚才那样。当然刚才我给了一个不好的示范，我说我今天创了两个slave——你现在也可以立即拥有这个DeepSeek V4的slave。然后你可以想：如果要最大化两个、三个或者更多agent，你应该怎么把任务分解，应该怎么确定提交的策略——什么时候你的agent应该提交，什么时候应该合并。然后你就可以把刚才讲的所有版本控制的概念带到你的开发流程里。所以重要的是这句话：版本控制是工具，它蒸馏了人类过去软件工程很多年的经验——人类要这样开发——然后在这个工具上，你可以发展出属于你自己的软件工程的直觉和经验。

这里有很多学东西还是有用的意外。除了我后面再讲怎么做软件管理，最近我看到一个蛮有意思的题目。我又带着这个模型——淘宝上大家都很喜欢，作为一个面试题。不知道为什么就在网上刷到了，一般是小学生考级的题目：汉诺塔都会，会有一个额外的要求——你所有的盘子的移动只能往一个方向。比如我现在简单一点，两个盘子：移过来，这个方向移是可以的，这个方向移也是可以的，就是要只能往一个方向移动，折回去不允许。

三个盘子的时候就能看出问题了。如果要移三个盘子，我希望先把两个移到中间——假设两个已经移到中间了——那下一个就是把这个盘子从这里移到这里，这是汉诺塔正常的移法。但是在这个限制下你做不到：你不能把它移到这，你只能往一个方向移动。你很难想象小学生要做这样的题。然后要输出方案——如果现在是你们，你们就在保研这个机制下——保研机制就是小学生难度嘛，你碰到这个题了，要输出方案或者输出这个数字。反正盘子数也不是很大，但你确实需要一个方案，需要理解这个问题。

当然我讲的不是这个汉诺塔的故事。这个汉诺塔的故事是：递归的时候，你现在要把它移过来，为了移过来，你先要把它移到这里，让最大的盘子向右移一个，再把它移到这里；再让次大的盘子移到这，再把它移到这里。所以相当于是你考虑最大的盘子的最优解：它总是向右移一个、再向右移一个。当然我拆开来讲，是因为——我能用这个吗？在这啊，我准备了一个小例子，写了一个这样的程序。就是我刚才说的：如果我的下一个目标不是目标的话，我只有最大的盘子，我总是向右移一个、再向右移一个，所以它是最优的——最大盘子的移动是最少的，这是不可避免的。然后剩下的也就基于inductive归纳法，我也是最优的。有点难，对吧？你很难想象小学生能做这样的题。但这不重要，重要的是我们现在要推出这个产品：我要把这个东西卖给小学生，那我怎么样才能最好地把这个产品卖给小学生呢？

### 8. 付费增值服务与 AI 助教设想、信息系统设计的需求梳理 / 项目早期不应使用 multi agent 与观察 AI 的行为

当然是提供付费的增值服务。这个小学生可以在这里写代码——我的代码是可以随时编辑的，比如我可以再写一个，他就错了。我的可视化是随代码运动的：比如他错了，就可以找到——找到我这条语句试图把一个蓝色的小盘移到大的上面——同学们就能找到bug。那如果我要挣钱，我要提供增值服务：现在还是一个纯粹的playground，可以写代码、运行它。然后这个时候我要提供一个AI助教——当然这个是不是不太好？开玩笑的，我们还是尽可能以一个便宜的成本提供给小朋友们。当你实在做不下去的时候，就可以点一个叫"我要助教"的按钮，然后DeepSeek的token就开始燃烧。这样我可以收取比你DeepSeek原价更贵的token费，记在你的账户上。因为我的prompt是我独门的——我作为一个有经验的老教师，可以把自己蒸馏成prompt，敏锐地知道这个小朋友的问题在哪里，给他提供个性化的指导。

好，这个时候我就涉及到要做一个信息系统了。因为这个事我让学生来做，我自己没有时间——我竟然有这么好的市场机会，竟然都不想挣这个钱。然后学生在设计，我看了那个学生和AI聊完的那一版设计，也让GPT帮我大概梳理了一下需求。这是GPT的原话：一个API应用，一个关系数据库，一个对象存储；需要异步点评时再加后台任务进程；数据库关系和记录，大课程包与完整轨迹存放对象存储，任务量小时数据库任务表就够用。这是一个非常正常的——如果你们上软件工程课，那太正常了。你看GPT嘛，它是一个语言模型，但我不喜欢这个设计。

为什么呢？因为我不知道你们有没有用过Overleaf，跟别人协作过文档。Overleaf有一个功能：可以把它当成一个git repo导出。我最喜欢这个功能，是因为我要给学生改论文：给学生改论文，我就可以直接agent启动——把那个论文克隆到本地，我就不需要忍受网页界面了。然后我打开我的Codex，让Codex直接写一个脚本，给每一个.tex文件修复语法错误，我可以给一个很长的prompt让它遵循，论文质量就改好了。我跟学生说"好了，改好了"。然后我们说回到这个Python playground：我难道不是应该学生在每改一次的时候——比如我编辑了，或者点了运行，或者切换了——就自动做一个git提交吗？然后我就可以把AI的点评——比如我申请AI助教的时候，它转圈圈——在这个git提交上面产生一个分叉，一个一个comment。GPT没有算到的是：我产生一个这个东西的成本，远远大于把剩下的东西persist下来的成本——这个成本是忽略不计的。而当我用数据库的时候，确实得到了一些好处：总体压缩的可能更小了、性能更高了，但这其实不是我要的。因为我的本质需求是版本管理。所以我甚至在最早期的时候，可以把我的代码库和这个东西连在一起，把关联关系放在我的代码库里。

然后直到——小朋友的代码就直接存在我的代码库里，我可以探索性地在上面创建git历史记录——直到我认为整个的、比如说文件目录的格式、commit message的格式、我怎样使用这些文件都收敛了，我再把它迁移到数据库。这都是可以的。我觉得这挺好玩的。你们学任何东西都是有用的：学git是有用的，学multi agent的管理，你就能够有一个机会想到一个和别人不一样的、不太一样的设计。

那么接下来我们真的可以干一件事了。项目的早期阶段，你肯定不能用multi agent。项目的早期阶段，你就是包工头：先找一个能力比较强——你能够用到的最强的agent——跟它多轮对话。所以我要告诉大家，你们现在开始干就比什么都要好。我决定现在就开始，直接打开课程作业——我不知道会发生什么，完全没有事先准备过——我还是开两个吧。

我们有两种办法。第一种是直接回车——我觉得每个同学都可以体验一下，当然今天我来替大家体验。我觉得更好的方式是观察一下它会做什么。有时候AI的直觉和人的直觉有点不太一样：如果你用一线模型，它会进入一个plan mode，跟你确认一些事实，然后再生成一个workflow。如果你们看过，其实挺好玩的：比如Claude Code，当它需要执行一个比较复杂的任务的时候，它会生成一段JavaScript、一段TypeScript，这个TypeScript里有一个函数叫agent，这个agent里是一个自然语言。当它用这种方式来组织workflow，它甚至可以有循环——我有好多任务，它可以在循环上面来解决这个workflow。

然后你看到它就直接开干了——用魔法对付魔法，只能用魔法打败魔法。这个300 token per second实在是太恐怖了。好，OK，不管了，先让它搞一搞。然后你发现这就是我前面说的上下文工程或者提示词工程里最危险的一点：你提示词里的每一句、每一个词，self-attention都会看到它；因为AI现在已经被训练成了prompt的舔狗，它有一种没有办法往外拉的倾向，必须要遵循你的指令。所以当你把这个需求——尤其这可能是一个讨论稿的需求，像我这样一个比较开放的需求——丢给它的时候，它会过度遵循指令，最终导致它生成一个确实满足了指令、但其实不是你想要的东西。

### 9. 实验要求的言外之意与 AI 生成 slop 的 intent gap / 软件工程以不变应万变、版本管理三件事与 AI 生成的架构风险

你回头看那个实验的要求，它是有言外之意的：核心其实是这一句话——"实现一个持续为你工作的个人助手"。这句话最重要，其他话相对来说没那么重要，那些只是一些解读。你觉得12345哪个比较重要？每个人都有自己的观点。对你们来说，如果想实现一个个人助手，什么最重要？你实现的第一个feature是什么？最大的就是你可能在一个月以内遇到的最大的痛点问题。学习，对吧？高效的学习和复习——因为你们要卷成绩，所以这毫无疑问是最重要的学习方案。最好是这个agent能够自动从外网上面收集数据，把它以层次化的方式归档，最终给我一个比较好的界面——这是你最想要的。然后你看，我估计它十有八九没有做。

我看一下。我要问它——其实我想要的是一个比较好的学习助手：能收集外部信息，综合总结，根据我的进度学习，看哪部分能实现这个功能。读一读，然后它在做database——你看它在做database。可以说，在没有你精心设想、讨论过的时候，AI基本上就只会生成slop，只会生成slop。你看它，email，没有，对吧。也就是说其实你要的、你脑袋里所想的那个东西——这就是我说的，你的intention和你的specification之间是有巨大gap的。但是一旦这个模型看到你要实现这个，它就真的去实现它了。

然后我觉得它肯定做了一些不好的事情。比如虽然我提"一号"的时候，我真正需要的是一个browser use agent，它能帮我在各种网页上处理；一号只是一个作为测试的出口——它能把我的个人信息填到教务系统上面。所以我第一步实现的，就不需要在这个教务系统上做太多的设计，你做过度的设计反而不好。然后这个和刚才我看给大家看的那个例子非常相关：你看起来它做的所有事情都是对的——从readme.md来看，它做的所有事情都是正确的，没有一个错误——但最终它得到了一个你不想要的东西。

然后我看现在有没有git提交了——它甚至都没有创建一个git repository，对吧。这就是你不跟它讲。当然我觉得如果Codex的话，它可能还是会有初始化一个目录，或者它会问你"这个项目应该怎么管理"。如果我是成熟的产品经理，老板跟我说……以后我肯定会跟我的团队沟通一下：项目怎么管，甚至在写下第一行代码之前都要讨论好协作怎么做、项目怎么管、每天什么时候开会。agent很好玩，它就直接上手就做，它觉得OK，这就是一个用一次就丢掉的东西。感觉它烧了我不少token也无所谓了——我参与了DeepSeek的内测，它送了我1000块的额度，到现在还没有完全用完。

所以你们在刚开始的时候还是回到项目、回到管理：脑袋里要有一个这样的模型，不能直接把任务丢给agent。你现在想的是：第一件事一定是创建一个空的项目，创建完以后，你就会想下一步要迈向哪里。下一步我也给大家展示了——不能这样，不能是这样的——你需要的是往前再迈一小步、再迈一小步。所以你发现，现在AI从零开始做一个东西、做出slop的难度，比它到一个成熟的项目里做一个维护性的任务要大很多。

我们对软件工程真正的要求——或者如果我要跟一个team、一个学生去谈论设计一个什么软件的时候，我的问题是：你能不能以不变应万变？也就是说你现在设计的架构、流程方法，能不能抵抗未来需求发生根本性的变化？你马上就看到在刚才那个例子里：数据库，我说要生成一个挣钱的产品、挣宝妈们的钱，但我真正需要的是一个能扩展的架构——当未来有别的需求来了，AI模型发生了变化，或者合作模式发生了变化——AI助教有可能是文字的、图像的，有交互的、没有交互的。各种各样的需求在不断变化的时候，我还有没有可能用最少的变化去应对需求的变化？

而这恰恰是大家——软件工程课也不讲，数据库、操作系统课也不教。大家都说"操作系统是长这样的"，但你为什么今天会看到一个这样的操作系统、这样的数据库？数据库为什么要这样做、并发控制为什么这样？都是有原因的。软件工程最不一样的地方，就是它面向未来需求的变化。

所以如果你们要——这两节课讲版本管理——你要记得版本管理做的三件事：记住现在、记住历史、记住教训。这在agent时代和软件工程古法编程时代都是成立的。你需要记住现在，是因为你必须有一个repository——不管是这个形式，还是现在的C、C++、Python、JavaScript项目，你都需要把文件管起来。你记住历史，是为了有一天这个东西你不要了、或者删掉的一个东西最终发现是有用的，你还可以把它捞回来。在提交的历史过程当中，你能看到你是怎样演进到某一个点的，发现这件事情失败了——这个失败可能留在这里——然后你回到另外一个点，再开始另外一条正确的路线。这些东西都在版本控制里，这些lessons不停地警示你：你需要怎么做，需要怎么样从第一步开始迈出向后的一小步。

那肯定显然不应该是——看，它已经实现完了吗？"提交人民奖学金申请，准备退课"——看有没有git，哎，它倒是做了一个提交，直接一个提交。引擎全部是真代码，手机端是真HTTP服务，Pi是集成的，模拟的部分邮箱是没有的。哎好啊，它有一个入口层、一个编排层、一个能力层，还是一个非常非常典型的架构。数据层——我就不试图review了。但显然它把这件事当成一个业务逻辑系统来做，这其实有非常大的风险：它看起来已经像一个教务系统了。这个软件已经看起来像一个教务系统——我下节课就会讲讲教务系统。

### 10. MVP 范式、文件目录优于数据库 schema 与邮件 Agent 流水线设计 / 好架构的标准、数据库设计的技术债与从最小精巧架构开始

其实现在更符合主流的best practice，如果你真的要从零开始构建的话，要用一个叫MVP的paradigm——minimum viable product，最小可行产品——有一个最小的验证版本。有一句话叫"the biggest risk in product development is building something nobody wants"。你看它做的东西就是我不要的，这个东西绝大部分内容其实不是我要的。我刚才在它登代码的时候解释了，我其实想要的是什么。所以如果你要做一个最小的版本，它逼迫你要想清楚：什么样的需求才是你绝对要的。

刚才我已经说了，如果我要做一个个人的助手，我最想要的是它能让我学、提升我学习效率的能力，和提升我工作效率的能力。你总结出这两条以后，你可能在第一个MVP里面没有任何数据库——因为你会想到，任何时候当文件系统膨胀的时候，你都可以跟agent直接说"好，按照这个数据的组织帮我提炼出一个数据库"，这个问题就结束了。所以你不需要在刚开始的时候就做数据库：一旦你带上一个数据库，每次数据库重构都需要让agent做database migration；但文件系统不一样，文件系统你自己就可以在你的文件管理器里调整目录结构，逐渐梳理到你舒服的结构上。你在里面调文件，和去调database schema，你的心智负担是不一样的。人类对直观的东西已经训练得非常舒服了。

文件目录在计算机里面操作，你从小——从小学上电脑课的时候开始——就做这件事了，所以你对这个模式非常习惯。但一旦你说要操作一个database schema的时候，你们很多同学还没学过数据库课，你根本不知道它是什么。在你面对一个未知的东西时，你需要强行做一次概念的翻译：我这个东西在脑袋里是这样的概念，要翻译到数据库里是这样的。那你不如用一个你已经适应了、熟悉的system，用最简单的方式帮你管理，比如说文件形式的学习资料管理、学习资料的进入、通知消息的进入。甚至到现在，我自己回邮件的那个agent都没有用任何数据库。

我的流程大概是这样的：我的agent会收我的邮箱，然后把那个email id放到我的一个共享的云盘同步上。然后那个email id里面会有它解析出来的内容，比如我回复的草稿、这个邮件的分类、是不是垃圾邮件，然后再由下一级的流水线去处理。也就是说，我先要明白的是：我的系统里面有哪几级流水线，这几级流水线之间应该怎么协作，哪些东西通过云盘。然后比如因为我很喜欢云盘，是否引入云盘要做一些架构的修改——我希望邮件和资料等都和云盘保持同步，这就叫需求的更改。

我现在不知道它的架构做得好不好，我让agent帮我看一看。也就是说，什么是一个好的软件架构：你在当前时候有一个需求，现在实现可能是满足这个需求的；但当你的需求发生变更的时候，你相应做出的那个变化是摧毁性的、是背上一个技术债还是别的，那就不知道了。

然后我们来看一下它的设计：它有一个assistant.db，个人资料放这里，邮件归档也放这里，索引、草稿仍然在db。现在看起来还不会引起很大的问题，因为绝大部分都是这样的，数据库确实应该不会引起特别大的问题。但是随着这个项目的不断进展，你就会发现有一种开发方式是这样：你上来就是一个大的，然后好几大步就把需求都实现完了，然后就拖着这个技术债不断地往后迭代、往后加功能加功能。

还有一个是：你从最小的出发，就得到一个特别精巧的架构。我举刚才那个例子的原因：当你发现我用Git管理学生的提交以后，很多事情都变得非常容易，而且我自己控制起来也轻松很多——直到我遇到性能瓶颈之前，我都不想要把它迁移到任何一种数据库。然后这也意味着，你早期的prompt对整个项目走向的影响是最大的：你最早的那个"我直接把readme给它，还说我要做一个MVP"，都会对项目造成很大的影响。我下一节课——周日——就会进入软件架构和构造的内容。好，今天下课。
