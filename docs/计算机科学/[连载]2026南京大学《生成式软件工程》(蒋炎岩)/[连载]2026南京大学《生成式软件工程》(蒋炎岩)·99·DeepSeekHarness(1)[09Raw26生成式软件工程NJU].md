## 总结

- AI agent native 时代，软件工程和版本控制的基本假设需要重新审视：agent 像公司里的员工，任务与 repository 的关联需要不同的锁机制。
- 架构的本质是在受限和自由之间做取舍；MapReduce、LAMP、Event Sourcing、操作系统进程等案例说明：架构一定要与需求匹配，否则就会从助力变成阻力。
- DeepSeek Harness（DPC harness）以 microkernel 和 everything is a plugin 为第一原则，用 CORDIS 管理插件生命周期，用 append-only 的 session event 日志（event sourcing）作为唯一 ground truth，并通过 event bus 实现插件协同。
- 干净的概念体系（session、agent loop、UI slots、projection）让插件几乎以无侵入方式观察和扩展系统，从而支持 trajectory 调试、text UI、类 VS Code 界面、creator mode 等大量生态功能。
- 插件并非万能：语义冲突（如多个上下文压缩插件叠加）、状态管理与 essential complexity 仍需架构之外的机制；但好架构带来的价值是形成互相增强的软件生态。
- 通过 SuperApp bridge（如 WPS 对象 hand off）、dynamic UI（模型输出 HTML+JS 卡片并通过 event bus 注回上下文）和接数据库插件完成填表等例子，展示了 AI native 应用走向操作系统式闭环的可能性。

### 1. AI agent 时代的软件工程、版本控制与 DPC harness 切入

我们已经讲了很多软件工程的概念，我已经说了1万遍了，就不再说什么是软件工程、什么是项目、项目管理。因为这些概念如此基础，在今天的 AI agent native 时代，它们不断都在被重新更新。就在上周，Anthropic 说 Git 他们已经不够用了。Git 不够用——其实我在上这门课、刚开始讲版本管理的时候就提到，我们确实会有一天遇到不够用的情况，这是很自然的。因为上学时你自己就是一个 single-thread agent，学 C++、学 Python、学 JavaScript，然后写自己的项目；但当你拥有 agent 以后，你立即就拥有了一个和现代公司一样的架构：你就是那个 CTO，你要负责全部，可能你不需要写代码，所以底下又有好几个架构或者产品 UI，然后前端后端有好多个 agent，每个 agent 又可以带好多个 sub agent，甚至 sub agent 还可以再创建出更多的 sub agent。其实你是存在一个组织架构的，否则你不可能管理一个复杂的需求。

我们讲，你做一个软件工程产品，面对的是各种各样的 essential complexity 和 accidental complexity。这个时候我们就需要一个版本控制，你还是需要一个 repository，因为你最终交付的还是产品，这个产品最终可能要经过 CI/CD 去上线、给大家提供服务。那么很自然地，在任何时候每一个人收到的都是一个小小的 task；从 first principle 去想，它一定是和 repository 里面的某一些部分是相关的。所以你这个 task 可能要重构一个 subsystem，或者要在某个地方加一个功能，它可能会影响到一些模块——各种各样的 task 在这个系统里面的样子也是不一样的，它会覆盖的东西不同。所以那个锁的方案其实还没有用到——我说的最好是给它加一个锁：这个锁有些可能是只读的（read-only），有些可能是 write 的，也有些可能是 refactor 的，锁的类型也可能发生变化。比如一个 refactor 类型，或者一个小的 fix（minor fix 类型），虽然它是写锁，但它对架构不产生 breaking change，所以多个小的 fix，只要它们互相独立，我其实应该可以并行执行。所以虽然我可以借鉴操作系统里面的锁（先上锁），然后借鉴数据库里面的锁（先做、然后再做 conflict detection，乐观的和悲观的），我们应该怎么设计这个版本控制，慢慢会从组织架构上面有一个答案。但我们毫无疑问能看到世界在向这个方向推进。

所以我觉得，因为概念已经讲得差不多了，我们还是应该回到一个比较具体的项目上，来看如果你真的要设计一个产品，整个流程会是怎么样的。那我们肯定要选一个 AI native 时代的产品，那我就选了这个 DPC harness（DeepSeek Harness）。正好我前天在北京参加了他们那一次线下聚会：他们很多同学就像你们这时候那么大，他们可能也不是像我这样写过很多代码、经过古法编程时代，他们可能也就是对着 web 去许愿编程，但是他们愿意到这里来跟大家交流一下，所以很有意思。他们可能经过几年的成长，就会成为一个非常核心的开发者。所以我觉得有必要讲一讲：如果我们要从零开始构建一个 AI native 的产品——当然不会做成那么复杂——你们会遇到什么样的问题。

然后从这些具体的案例上面来讲解这件事情到底怎么发生。里面有很多细碎的东西，我今天会讲到需求、架构，以及整个软件系统的设计会是什么样的，我们怎么样在这个 DPC harness 上做二次开发。然后下一节课我可能会讲整个 agent native 开发更细的东西，因为 DPC harness 里面有非常多的 CICD。我看到有同学在评论里说，上节课讲了很多，但看起来好像什么都没讲。确实是这样的，因为有些事说起来简单——网上有很多 skills，你可以 grill me、可以 grow with docs，然后你有 superpowers——但真正拿过来用的时候，你会发现比如你们也许试过，用 grill-with-docs 去做那个 lab1，马上就发现它陷入无穷多你不想让它管的事情里面，尤其是当你面对未知的时候，你不知道它在干什么。

有的时候那个 skill 会反复地、疯狂地 find out 那个 sub agent，做一些你可能觉得没有必要的测试或者 validation。这些东西可能在某些场景下——比如我真的在公司里开发产品的时候——是成立的；但你们最好是自己去摸索一下，有一个切身的感受。所以我今天也为大家切身地摸索一下：我已经把编译好的 DPC harness 准备好了，我可以问它，应该是可以正常工作的，就是一个 DPC harness。我不知道你们有多少同学使用过一个相对比较复杂的开源软件，并且真的动手去改过它。比如在前 LLM 时代，你把它运行起来都很困难，但我现在完全就是许愿式运行：从昨天到今天，比如我在我的这台机器上面部署它，包括我外部的一些东西，我全部都是许愿式的——我只要知道这个项目可能可以被编译，那么 OK，让它去做好。

那假想我们要实现一个 DPC harness，应该从哪里开始呢？肯定是从上上节课那个 mini agent 开始，大家应该还有印象，这就是一个 agent harness。几乎所有的 agent harness 都遵循这样的循环，因为大模型推理是 response API，不管它是返回一个工具调用还是什么，它都是一问一答、一问一答，不管回答的是人还是工具。那这个 agent harness 能用吗？能用，它完全可以工作。我昨天在高铁上——周日的时候——突发奇想：既然我们要讲 agent harness，那我们能不能让我们的 agent 生成一个、做一个真正不 trivial 的任务呢？因为这个任务可能确实会比较长，而且正好新模型发布了，我就给它一句话，真的是一句话：我要一个比例基本真实的南大仙林校区的三维图。

你们有没有预期到它会输出一个这样的结果？这还是很不错的，虽然有些地方不太对，比如你看计算机楼是十层楼，但十层楼这个高度明显做得不对；但有些又做得相对比较正确，比如图书馆的建模还是相对比较好的，尤其是楼从 top-down 来看，几何形状被正确地保持了。所以如果你观察 agent 的 trace，它是怎么做到这一点的呢？是因为我们的网络上面有很多的数据源。其实在我上学时代就发现了这个宝藏：有一个网站叫 OpenStreetMap，开放的地图，你能找到各种各样地方的地图，而且它的地图其实很细——比如如果这是一个篮球场，它真的会划出篮球场的那条线。

所以他还没有用全部的模型。他从那里爬了数据，爬完以后自己根据自己的想法建了模型。比如他有些想法就不对：你看到因为在地图上没有东西的部分就标上了绿色，他说这是一块绿地，绿地可能有小公园，或者有些可以休息、椅子休息的地方；然后他把绿地……比如在这个大门进来的地方，这个大门也画成了楼，然后在大门进来的地方铺满了树。所以你仔细看，这可能不太好，你需要给它更多提示词：让它把每一块区域都单独划定出来，划定出来以后再仔细思考这块区域的功能、它应该是什么样，然后再给它做一个精确的建模。然后它会花更多的 token——十倍 token——再把这个修一点，就可以得到一个更好的版本。

你在网上看到的很多，不管是用 GPT-4o 还是 DeepSeek（他们说 DeepSeek Flash 的新版图形能力很强），也都是用这种方式：它有一些 skills，你就不停追着让它一遍一遍地验证，然后通过烧 token 的方式，从一个还不错的基础上最终得到一个……比如你想，我相信很多同学都梦想着做一个南大版的 GTA，然后可以在里面身临其境地突突突，如果你想的话，这就是一个很好的 starting point。因为你有三维模型了，并且你知道可以 instruct 它去构建——比如什么地方是可以走人的、什么地方可以蹲点——你就可以构建你的游戏逻辑，这完全可以工作。

### 2. 网络中断、重试与需求膨胀：agent 产品的 essential complexity 与 MVP

它不能作为一个产品——作为我在客场给大家玩一把，肯定是可以的。它不能，因为上一个版本假设了网络服务不会中断；如果你只是一两轮对话，其实感受不到这个问题。但我在高铁上的时候，它给我来了这么一出：我大概已经跑了比较长的时间、有些中间结果了，然后突然间在高铁上网断了；网断了以后，进程直接终止，终止以后我这个 150 行的 mini agent 是没有会话保存功能的，也没有恢复功能，也没有网络中断以后重试的功能。那断了以后，我就只能要么从零开始让它继续，要么让它重新再做一遍。所以这其实就是第三重 complexity。

你再往后想，如果你要做一个真正的 agent 产品，比如一个 DPC harness，那你怎么应对 API 中断？首先你需要重试——你们都见过 coding agent 的各种重试行为。这时候你又需要想：重试到底要有多少间隔？因为如果你在不同的环境下——打个比方，你在美国的数据中心访问 OpenAI 的服务，和你在中国挂上 1 万层梯子访问 OpenAI 的服务，那是不一样的网络环境，所以 timeout 等等也不一样。所以你发现，API 中断时如果设置一个重连、重试的时长，或者连接中断的时长，那又变成了一个复杂的问题。

然后如果你一次失败以后，第二次应该以等间距的时间再试一次，还是应该慢慢拉长时间间距？因为你们学过网络，知道有 exponential backoff 这样的探测特性：你用一秒钟以后失败了、再一秒钟以后又失败了，那大概率下一秒钟它还是失败的，所以你可能要等两秒钟、四秒钟、八秒钟，直到网络恢复可能是以分钟级。就像我刚才出现了这样一个物理世界故障的时候，启动就可能需要两三分钟才能重新回来，那都是非常大的复杂性。你看我让 AI 帮我总结一下，它还说出了更多莫名其妙的东西。在实际的产品当中你还会面临更大的挑战，比如你的服务端和客户端可能是不一致的：你的客户端发起了一个请求。

比如说支付。服务端收到支付以后就把这个订单下了，因为它还涉及到和其他系统的确认，它不能等——你不能等所有做完以后再由你来 close 这个 transaction，而是收到以后就要把这个 transaction 给 commit，它做不到（不能等）。因为这可能是你订下一个淘宝单、或者买一张机票，你的钱送给银行或者送给航空公司的时候，这个 transaction 就已经结束了。所以它会在服务端完成，服务端有非常复杂的架构可以支持这种可靠、比如一个订单的完成。但是你在这个订单发出去以后，手机断网了，那你怎么办？你在设计这个产品的时候，会看到手机上转圈圈；转圈圈以后你的手机应用不能 crash，得告诉你网络中断了，所以你的订单处于一个"我不知道"的状态。可能是下成功了，也可能是下失败了，但因为和服务端缺少同步，所以它不能决定自己到底是什么状态。所以你看到，我们在软件系统设计的时候有很多这种 essential complexity，它就是复杂的，没有办法避免。

然后你再看，如果你要设计一个 agent 产品——不是一个 150 行的 agent——那就涉及到比如项目的管理。你的 agent 同时可能会在好几个工作目录上面工作，这是大家不管用 DPC harness 还是任何一个 coding agent 都可以做到的。那你就需要一个 dashboard，能够在多个项目之间切换；然后 agent 需要访问项目相关的工具、skills；在运行过程中，它的工具调用需要有沙箱和权限。那你就回想到你平时用 coding agent 的时候都看过它问你、向你要 approve 的那些产品设计——这就会带来一个非常非常长的产品需求规格说明书。我又让这个 AI 来假装自己要做一个 Workbody——这可能是你们老板的要求："我们公司今天要出一个产品，要对标现在最好的、卖得最火的、和人交互的 agent。我们调研一下，DPC harness、Workbody 谁卖得最多？那 Workbody 卖得最多，你就去做一个吧。"

如果要这样，你看到 AI 还是挺有智慧的。虽然因为我今天讲 DPC harness、DPC harness 肯定走了一条完全不一样的设计路线，但 AI 确实想到了一些有趣的东西：它会先想一些典型的应用场景，比如用例图这样的东西——"把这个文件夹里的本周项目记录整理成周报，列出延期事项，生成 Word 文件"，这是 Word 管理里面非常常见、普通人用的。然后它就在这个基础上列举了一些潜在的应用场景，开始疯狂地列需求点。比如它要求历史的检索与任务的复用，这是 agent 产品所需要完成的非常典型的功能；模板与偏好、执行预算与用量、账号与数据管理、外部内容与指定隔离、用户反馈与问题诊断。当然实际上还会多得多，它还有很多非功能性的需求。

那如果你直接让 AI agent 去实现这个需求，你们大概率就会陷入一个 slop 的状态。因为 agent 有一个非常强烈的倾向：它要直接把这个任务完成，不会动脑子去想到底未来还会发生什么。所以做一个产品和做一个 MVP 其实是不一样的，但 MVP 可以帮助你看到这个产品到底有什么真实的需求。在你使用 MVP 的时候，你的假设会不断地被 validate。像我的这个小 agent，就做了一个不切实际的假设：网络是稳定的。

### 3. Growbot 冲击与快速复刻：需求突变如何冲击架构

API 是稳定的，但这个假设不成立以后，你的需求其实就相应地膨胀了。所以如果我们要设计一个 agent harness，面对的真正的挑战其实是需求的改变。比如刚才我们已经做了一个面向 Workbody 的办公应用、办公场景的非常详尽的需求报告，然后你已经带着 AI 写了 50 万行代码并且已经上线了。然后突然今天 Growbot 火了——Growbot 是一个新的交互方式：我们可以把 agent 当人，当人的时候每一个人就有他自己的记忆，所以我可以比如拉一个群，让两个人一起来协同完成工作；我也可以让人比如每天什么时间干什么事，这都挺好的。

那么 Growbot 火了以后，你发现它的交互方式就跟刚才我们做的那个需求完全不一样了。我们做了一个非常详尽的需求，需求说好：我们的左边栏就是项目，右边栏有几种，比如 pinpoint view、什么 wall、什么 wall 好。然后如果有一天你的老板突然说："哎呀，我们下一个版本就按照 Growbot 做吧。"什么叫"你怎么杀死一个程序员"？你只要改需求三次就可以了。因为你之前的所有需求假设全都崩塌了，交互模式的根基崩塌了——所以应对需求的改变是非常有意思的。

所以不管大厂做了一个多么好的架构，它那个架构可能在性能上面达到极致、能够在功能性需求、非功能性需求上非常好地满足上一个版本的设计，但一旦这种摧毁性的事情来了，大厂就必然要开始疯狂拉通对齐、闭环、沉淀、复用，最后再到下一个版本。这没办法，确实是没有办法。因为大厂毕竟有交付质量的要求，它其实做了一个选择：它期望能够极高质量地交付需求，所以它的架构可能会做得相对保守一点。

相比之下，比如这是 DPC harness——我没有装它——但当你看到，光速就有了不止一个人去 release 了这个 dsh bot，然后这个 dsh bot 看起来就跟 Growbot 像素级复刻一样。它在这里像素级复刻：可以设置多个 bot，你可以拉一个群，甚至这个群还有一个像群一样的图标，非常真实，然后你可以跟他聊天——光速复刻。而且甚至我觉得在这个基础上，你可以外扩出很多它没有的功能。比如 Growbot，你今天觉得它哪一点不好——我觉得它不好：它希望给普通人用，所以不给我开放任何编辑它的东西的权限、它的配置的权限。

但对我一个 programmer 来说，我真的就是想把那个 configure.yaml 拿出来自己改一下，或者那个 prompt 提示词给我、我改一下，因为我懂得怎么改提示词；但可能对 99% 的人来说，他都不知道应该怎么跟模型对话。所以 Growbot 是一个很成功的产品，但如果你不满意，你可以 Vibe 一下，在这里加上别的功能，比如一个 multi-agent 交互的 dashboard，你就像是一个老板视角。哎，又回到这个图了：本质上 Growbot 是想要构建一个这样的组织架构，比如以项目组人、以项目组为单位，你每次只要和项目组或者你的 CTO 交流——你就是 CEO 了——和 CTO 说"去把这个事情做了吧"，然后他再把任务一级一级地分下去。

那我有没有可能，左边不是这样一个树栏的结构——你可以做这样的需求——而是做成一个树状的结构，代表你的部门、你管理的部门，让你有这种老板的沉浸感和体验感？然后你也不要右边的，也不要跟他这样聊天了，把它压缩小一点：你有一个老板似乎好像自己坐在办公室里，给你提供一点情绪价值，然后马上下面就有人可以去 Vibe 这种。

### 4. 架构是受限与自由的平衡：从操作系统到 Event Sourcing

为什么讲这个故事呢？我们把时间倒回到 2026 年 6 月 10 号。那还是一个 coding agent 已经达到、大家已经意识到 coding agent 要变天的时候。那时候有一些主流产品，Claude Code、Open Code 这些都有，还有字节系的：那时候没有 Workbody，有 Coldbody。后来我知道 Workbody 和 Coldbody 其实共享了一整个 agent 层编排的底层架构。就在这个时候——我还特意看了一下，2026 年 6 月 10 号晚上 11 点，谁说 DeepSeek 不加班的对吧——有一个神秘的项目启动了，里面什么也没有。连那时候还有 CLAUDE.md，这也是一个很恶心的需求点：当你需要支持比如你的一个项目想要同时支持多种 agent 的时候，你就需要用它们都理解的方式去组织项目文件。当然好消息是，今天你不需要用 CLAUDE.md 了。然后做一个 MVP、requirement analysis，有一个 microkernel architecture。你看他从第一天开始，6 月 10 号晚上 11 点，就想做一个操作系统，他想造一个航母。

那这航母到底是怎么造出来的呢？我们就要回到讲一讲架构。刚才我们说，如果你对着需求文档直接让 agent 帮你做一个架构，那么 agent 的注意力就会在需求上。需求很自然地——比如这里面有一个东西叫工作区——agent 就会很自然地倾向于在架构设计里为这个工作区做一个 class，因为他不能设计一个什么也没有的架构（那样就没有完成任务）。然后它会涉及到工作区和其他东西的交互，这个设计肯定是需要的，比如和模型、和 agent 层的交互是什么。比如工作区里面可以链接到 session，session 可以向 agent 发送一个 chat，然后 agent 之间可以自己调用 agent loop 或者工具来做事情；同时他也可以把一些结果，比如绘制的 canvas，放到 session 上。那这个地方我们应该用一个数据库来存放 session。好，那这个架构就开始出现了——这是一个非常非常自然的架构设计方式，或者说在大厂里面也经常是这样设计的。

但是架构意味着什么？架构就意味着没有免费的午餐。当你做了任何设计以后——不管是这样的架构，还是可能 DeepSeek Harness 那样的架构——架构都是在受限和自由之间达成一个平衡。当你的架构确定了以后，模块和模块之间的边界就有了；边界有了以后，你就可以在开发这个模块的时候不用知道、或者说只要比较少地知道系统剩下的部分是怎么工作的。这样的好处是：你看我在第一天的时候，需求就分成了这样一个架构，分好以后每个模块就可以独立开发，所以马上就可以启动大量的 sub agent，大量 sub agent 就可以把这个产品堆出来。

但你做的这个限制就限制了我的自由度。当未来需求发生改变的时候——你可以这样想，当 Growbot 这样的需求出现的时候，你的架构如果不能适应那个未来的需求，那你就会不断地有这种抽象的泄漏，导致这个项目很难维护下去。但如果你做得太自由——比如你说"我要做一个创新性的架构，每一个模块都是一个 process"——那不管是工作区。

还是你的 session，比如 agent 或者是你的 UI，每个都是一个进程，然后每个进程之间都是发消息的（message passing）。那这个架构就非常干净、非常自由：我可以随便发消息。但它自由得没有任何用，它就是个 actor model。说得对，可能确实能这样实现，但是它没有约束：比如消息应该怎么管理？不像这个架构，它说这个工作区和 agent 之间是通过某一个 API、某一个队列（比如一个 session 的 message 队列）来管理的。那这个接口定下来以后，就只能做这件事，比较容易开发。但如果自由的话，你什么时候发什么消息都没有确定，你等于没有架构。越容易、越自由的东西就越不好开发；受限有受限的好处，自由有自由的好处。

所以你们带着这个想法去理解所有的架构系统，你一层一层的架构设计，它都是有取舍的。比如操作系统上面的进程就是一个非常好的抽象，但它非常自由——它当然就是为了让你在上层能够搭建各种各样的应用程序：你可以做浏览器、可以做 coding agent、可以做虚拟机、做任何东西，操作系统要提供这样的功能。但这个自由也就意味着，你看操作系统为了"到底要用什么编程语言开发"这件事，人类就吵了几十年，到底什么语言才是最好的编程语言。现在这个老梗——"PHP 是最好的编程语言"——已经见不到了；这个梗在我上学的时候还是非常流行的。

高级语言也是：你做得越自由，C 这样的程序就可以更好地控制机器，但带来的问题是可能会有内存泄漏、各种麻烦。受限和自由，你是没有办法达成一个完美的、都兼顾的方案，所以你只能在这个 spectrum 里面做一个取舍：把限制做到什么程度、把自由做到什么程度，其实每一个架构都有这样的问题。比如经典的 LAMP（Linux、Apache、MySQL、PHP）——PHP 是世界上最好的编程语言——它是一整套方法的架构，这个架构引领了我们整个互联网世界至少十几年的时间。WordPress 就是典型的这样的架构，很好；但当你要服务更多的人——要服务 1 亿人、10 亿人的时候——这个架构就扛不住了：它的每一个点，从单机开始到数据库，每一个点都是瓶颈。然后为了把它拆开，就各种抽象泄漏：分库分表，先让一个服务器扛着，最后服务器也扛不住了，服务器再拆开这个架构，就演进到了下一个版本的架构。

然后包括 event sourcing，我们讲 event sourcing 可能比较好：所有东西都是事实，你只要 append-only 地记下来，然后剩下的人看到的都是事实的一个 derivation。那架构概念很干净，就有点像这个，但它也不是没有代价的。因为你的当前状态是完全由过去的历史推导出来的：首先你要把性能做好，难度就会更大一点；其次有时候我们真的只是想 hack 那个当前状态。比如教务员就是想让你强行毕业——没有理由地想让你强行毕业。在一个月黑风高、没有人知道的时候，悄悄地你就强行毕业了。这种操作显然在真实世界中可能是一个合适的需求，但在 event sourcing 里面你就很难办到：你需要加入一个特殊的 event 和一个特殊的 event 处理规则，叫"强行毕业"。而强行毕业这件事情，因为它在 event 这个 persistent history 里面，又会被审计到——你又不能以"哎呀我也不知道那个时候是怎么回事"的理由来搪塞。

为什么这个同学可以毕业？因为谁 committed 的这个 event，当时就知道。所以这好像也是一件比较有趣、但有点危险的事情。所以每一个架构都有取舍：它牺牲了一些，但当然是得到了——可能是解耦合的系统，可能是持久化给你的好处，你甚至可以回退到任何一个历史的版本。所以基本上这个总原则就是：如果你的架构和需求是匹配的，你就是方便的。

LAMP 这样在单机还能够处理应用需求的时候，它就是最合适的架构，PHP 就是最好的语言；但当你的假设发生改变的时候，这个架构就可能会成为阻力。所以我觉得某种程度上，人类社会的进步就是不断打破旧假设的过程：新的产业要诞生，旧的产业要消亡；在旧产业消亡、新旧交替的时候，就有人才的流转，有些人就自然而然被淘汰了，老登们就被淘汰了，然后大家在这个接纳新事物的过程中，就有新的机会诞生。你们每个人都会经历过很多这样的、身边发生的事情，最终才能真正开始理解。比如因为我小的时候经历过很多次，包括我们国家的很大的变革——国企改革，你们可能只能听说过这些；然后到房地产的崩盘，然后到 AI 时代的来临：我们从互联网时代、云计算，到 AI，每一波浪潮的时候都有这样的新旧交替，这也是一种架构上的变化。如果架构和需求匹配的时候就便利，如果这个假设发生变化，你就需要一个更新的架构。当然我觉得在 AI 是产业超级加速器的今天，这个变化可能会变得更有趣一点。这些是 AI 帮我补充的，你们有兴趣回去看 slides 就行。

### 5. MapReduce 的成败与设计 agent harness 的第一原则

然后我要讲一个具体的架构变化的案例。在 2004 年的时候，Jeff Dean 和 Sanjay 发了一篇文章，某种程度上改变了 LAMP 中心化服务器的浪潮，这篇文章叫 "MapReduce: Simplified Data Processing on Large Clusters"。这篇文章非常非常好读，好读到你只要看这个例子就行了：如果我们要做一个大规模的分布式计算，你不要去写那个好长好长的代码，你只要遵照一个受限的代码模式，叫 map 和 reduce——这个 functional programming、Python 里面也有。

map 说：我有一个 list，然后有一个 function，我就可以把它变成另外一个 list，这是 map。reduce 是说：我拿着一个 function，然后不停地把元素喂给它——先拿第一个元素，再拿第二个元素，再拿再拿——但这个 F 如果有一些比较好的数学性质，比如有结合律的话，你就可以 parallel reduce 两个部分，然后再 reduce 它们的结果。如果你能把计算写成这个形式，你就可以用我的框架。

所以你看他做了一个架构上的取舍：它限制了你的编程模型，你只能这样写程序，先 map 再 reduce。当然它 reduce 的时候有些比较聪明的设计，比如它会把东西按 key 排序等等——它有一个排序、shuffle 的中间过程。然后剩下就是他做了一个系统的实现，这个系统实现藏在后面，你不需要知道它是什么；但好处就是你只需要写这样非常简单的程序。早期在 Google 内部是 C++ 的：include 一个 MapReduce 就好。

然后你就可以写一个 class，class 里面就说 map 是什么、reduce 是什么，就像写正常的程序一样。只是我不再使用程序里面基础的抽象（像 pointer、list 这样的抽象），而是一个系统包裹了的、可能会跑在不同机器上的抽象。然后就可以写出这样的代码：在一个分布式的文件系统上，我可以做计算，说我要 map reduce，我最多 2000 台机器，每台机器每个 task 用 100 兆的 memory，然后跑吧——它就可以自动地在很多台机器上跑完。对，MapReduce，所以这是一个引领了世界的设计。后来大家发现：哦，原来我们有这样的抽象层，我们写分布式的程序就真的变得容易了，而且还可以容错。

Google 那个时候遇到最大的问题是：这些机器，当有很多台的时候，整个系统就变得不可靠了。当运行一个很长的任务——比如整个互联网全数据的索引——的时候，那几乎一定会有一台机器要么掉线、要么出故障。所以你以前的基本假设——LAMP 的基本假设——是这个机器是好的。你们每一个同学在你们的电脑上面做大作业的时候，那个基本假设是"我的机器不会突然消失吧"。如果你的机器突然消失了，那你就摆烂了，你就跟老师说"对不起老师，我的……"，用一个社会工程的方式解决这个问题。但 Google 不能用这个方式解决问题，它必须用一个系统的抽象来解决问题。好，它成功了，它也失败了：因为这个限制只适合这种离线任务——第一，其实用起来不是那么方便；第二，如果你想要更方便地、比如处理及时来的数据（比如银行的订单），当这些需求也走向分布式的时候，MapReduce 就没有办法支撑它们了。所以我们需要更高效的。今天的答案是 Spark 这样的计算引擎，还有 Flink 这样的流式数据处理——当然 Flink 其实和函数式编程也有千丝万缕的联系。这是一个具体的例子，一个历史。

好，所以我讲了那么多，我说的一件事是：架构是受限和自由之间的平衡。那我们就可以来到这个：如果你要设计一个 agent harness，你的 first principle 是什么？我们看到第一个提交上面说"我们要做一个 microkernel，我们要做一个操作系统"。那操作系统意味着什么呢？意味着操作系统不需要知道每一个进程是干什么的。在 UNIX 诞生的时候，还没有桌面浏览器、也没有图形用户界面，它不需要知道这个进程是干什么的；但它能把那些进程组合起来，并且进程之间可以互相组合、互相使用。

所以它的 first principle 是 Everything is a plugin：所有东西都是可以插件解耦的。然后每一个 plugin 就像我说的，有点像 actor model，但它不是一个 actor model——你可以这样理解：如果我要把每一个插件都想象成一个进程或者一个人，让他们之间互相发送消息，那我理论上说可以实现任意的架构。这个架构只是说，我希望把每一个模块的 private state 都封在它自己的里面；当模块和模块之间需要交互的时候，你就给我发一条消息，然后我可能会给你一个返回。所以理论上说，你可以把任何程序、任何软件系统的模块都当进程提取出来，然后把模块之间的函数调用换成 remote procedure call（远程过程调用），然后任何一个软件都会变成这个样子。所以"自由"这个架构是没有用的。大家都在谈论 DPC harness 的时候——

他有一篇论文先发了一篇叫 CORDIS，里面有大量的公式。虽然 CORDIS 也是架构的一部分，但其实我今天不讲这个架构的部分，因为 CORDIS 负责的是服务的解析、依赖的激活，以及这些插件的 load 和 unload。这就相当于，如果把 DeepSeek Harness 想象成一个操作系统，那这上面的东西就是进程。我们知道操作系统里面该有一个进程管理：在一个进程退出的时候，进程所持有的所有资源都应该被回收——这是大家已经默认了很久的事情。就像你们写 C 的时候从来都不回收内存一样，因为你知道操作系统会回收。

而 CORDIS 的设计就是这个想法。当然它肯定不可能把所有 side effect 都回收，但在理想情况下，你的进程可以 declare 它需要一些资源、或者说它对系统会产生一些 side effect（比如它可能会依赖一些东西），这些依赖的东西应该被自动加载；而当这个插件 unload 的时候，依赖的东西最好能够自动卸载。就像操作系统在创建进程的时候会分配内存，那这些内存在进程被 kill 掉的时候也要自动回收。这显然是一个插件方面的机制。

### 6. agent harness 的世界模型：session、event sourcing 与 event bus 协同

但整个 harness 设计真正的难点在于协同：如果这些插件之间让你随便发消息、随便协同，那就全乱了，没有任何实际的好处——就跟我说的，每一个都是一个函数、硬链接在同一个地址空间里面，没有任何区别；不协同又没有用。所以真正比较有意思的设计，其实是你要构建一个 agent harness 的世界模型。我们的 DeepSeek Harness 里还有一个非常重要的、相当于所有进程共享的共享空间，关键的数据结构都存储在这个空间上。基于这个"进程"，DeepSeek Harness 还构建了更多的抽象：它没有特权的内核，所有东西都是 CORDIS 的插件，但这里面有更细一层的世界模型。

比如 CORDIS 下面的 session。如果我们要做 LLM agent，还是以大模型为中心的：这个应用无论如何还是以大模型为中心，所以它的 session——append-only 的 session event 日志——是唯一的 ground truth，然后模型的历史不是存储的，而是从 derived message 派生的。也就是说，它有一个相当于完整的事件日志，这就是一般说的 event sourcing，它也用了 event sourcing。所以它在"进程"的基础上又做了一个 event bus，event bus 上面再可以挂载各种各样的插件，插件还可以监听这个 event bus。然后在这个世界上有一个 persistent history，所有其他的能力都是在这个基础上长出来的。

它会做一些类型的检查，有 service definition 的 provider 和 consumer，以及一系列的权限管理。最重要的是：事件扩展点按照领域分类，也就是说系统里每一个插件都可能会产生一些事件，放到这个 event bus 上。大部分是用来规定消息的格式是什么、谁能够往这个 event bus 上面放东西、类型匹配不匹配——如果不匹配，TypeScript 是不会编译这份代码的。它做这样的限制，就像禁止你任意地往别人那边发消息一样，它要做这方面的限制。然后我发完消息以后，还允许我的一个插件去监听另外一种消息：当这个事件进入 event bus 以后，我的插件可以监听某一个事件，这个时候它就会收到这个事件的通知。

甚至还可以去修改这个事件本身。所以它相当于是赋予了一系列原子的能力，一个小操作系统。然后每一个插件在这个 bus 上面都可以看到，比如每一个插件都可以看到 LLM inference 的状态，比如我的大模型这次吐出来多少 token。当然它还有一些设计：有些大模型的事件实际上是不 commit 的，它的 history 里面可以有一个 open 的 entry，这个 open entry 代表这次可能还没有结束，所以大模型会不断地往里面送新的 token，这个状态就是不 persist 的；但这个状态依然可以被看到，这样我可以实时显示。比如你们可以看到 thinking，看到思维链动态的变化。这其实是一个事件，但这个事件是动态的——这是一些小的实现上的 trick。

比如 LLM inference，我收到这样的事件以后，有的插件就可以用来统计 token 的 cost 和 cache hit 的情况，然后把它放到 UI。它又做了一层叫 slot、slot-based 的抽象，可以把它绑定到某个地方。所以最早的时候我们在内测版本，这些东西原生都是没有的，真的就是白板一块、什么都没有。但这个白板一块，第一天就有开发者群里的同学做了一个 token 统计、上下文统计——他完全不需要干扰到系统里面任何一个其他部分，因为这是一个不侵入的功能：我只需要观察 event bus 上面 LLM 吐出来的 token 的情况，然后相应地更新我自己内部的状态。

所以还是这个模型：它希望把大部分的状态都放在自己的内部，然后只有我希望别人看到的事情，才以事件的方式放到一般的 bus 上，这是一个非常自然的设计。但他为了 LLM 显然做了更多的 specialization：它有三大抽象——session 是 list of event；agent 是接收输入、推动执行；还有一些用于装配的 UI slots。基本上有这些东西，你就能想到所有 Workbody 里面想要实现的东西，它都可以实现了。

然后比如我想要把它改造成一个 bot。DPC harness 有什么比较好的特性呢？你如果对这个聊天框不满意——比如你不喜欢这种、想换一种更 fancy 的方式来展示——你完全可以：你可以直接把这个 session 流……因为 session 流本质上、你看到的这个窗口，也就是一个从 message history 里面导出、算出来的东西。你说"我不要了，这个东西我设置成不可见"，然后我放一个我自己的东西。在 DPC harness 里面其实有这个 trajectory，你看它就是整个 session history 的两种不同类型的投影。

它可以把这个 history 投影成这样一个给人看的 UI，也可以投影成一个给 developer 看的 trajectory。我可以调试里面的东西：我随便让它 call 一下 bash，你可以看到它的工具调用、它的 payload 是什么、它干了什么、工具调用的结果是什么，还有一些额外的信息。所以你看它就是白板一块，但在这个白板上，通过它的第一方——这个第一方很重要：如果它对 event 的设计崩了，或者对 session 的设计崩了——

那整个后面这个 DPC harness 就不可能维护下去了。但如果它把概念体系建得很好，使得上面的插件绝大部分时候都只要 consume（非常少地、也对这个系统没有侵入地消费事件——虽然它有侵入的能力），我们就可以在上面实现任何的东西。所以我当时看完它发布以后，我就说这个"震惊瘫坐"、这个原子弹爆炸。大家可能没有意识到一个干净的架构可以给我们带来什么，它看起来就很平常。

比如它的 API 就是 session：我可以在 session 上面 append，或者注册某一个 event 的 handler 来在 event bus 上面监听，或者我可以从事实里面生成投影——我刚才给大家展示了，我可以 session.deriveMessages，从这个 persist history 里面导出 agent trajectory 或者 chat。其实光这个功能就非常好使，非常非常好使。

### 7. hook 机制、整体架构与插件生态示例

然后比如可以向 agent 提交输入：可以 follow up、可以 inject、可以 steer，这都是你们在用 agent 产品的时候用过的。比如你们在用 Codex 的时候，它模型正在推理输出的时候，你可以继续提问。但这个继续提问，你是应该等到这个工具全部完成（比如这一轮全部完成以后）再 inject，还是下一次工具调用——就是大语言模型的那一轮 chat completion 或者一轮 response 以后——就立即把这个新 prompt 注入进去，还是你要按 ESC 停下来再来？这是 agent 的操作。然后这个还可以持续地贡献动态的上下文，而 context……

这种 session.event 是可以 hook 一些还没有 persist 的事件的：有些事件，比如刚进入系统的时候，我是可以篡改的。而这个能力是整个系统设计里面非常非常关键的一环：它不再是说"我只能看，看了以后再推一个自己的新事件上去"，而是我可以比如把一个东西扔掉；或者你看叫 agent 下的 PRESTEP——在 PRESTEP 之前，我可以干一些事，这样我甚至可以做往 agent 的 loop 里面 inject 一些 prompt。

你们想想，如果在做需求的时候，你会怎么做这件事？我希望每一轮对话的时候，都把当前所在的时区信息、我所在的……比如有人要干坏事，你的电脑的一些指纹信息等等，注入到模型的上下文里，这显然是一个需求。而这个需求你可以写在需求说明里，然后直接在 build context 里（你们如果要实现一个 agent，一定会有像我那 150 行里也有的 build context）写一个；但我也可以在这个 agent 的 PRESTEP 时，放一个这样的 hook，然后把它的内容改掉。

所以基本上整体的架构就是：插件挂在一个总线上，然后有少量协作的接口，每个插件绝大部分的状态都留在插件本地。但是它们能够看到、感知到这个全局的 agent loop、session，以及可以看各种各样的 projections。所以每个插件都能很好地、按需得到它想要的所有信息：关于当前 LLM inference 到了什么进展、其他的插件做了什么，当然还是以大模型的推理为核心。然后这个设计的一切都是为了插件的生态：你们看到的比如这个 trajectory，只是它原生第一方发布的一个非常 plain 的特性。

但这个特性对你 debug 很有用——如果我们是开发者的话，很有用。在这个地基打好了以后，你会发现做任何东西都非常容易。比如如果你想为它做一个 text 的 UI——DeepSeek Harness 的原生设计是 web UI。

因为 web UI 里面有一些关键的抽象，比如装配 UI 的 slots，因为 web 可以呈现一个非常人类友好的界面。但如果你偏偏要剑走偏锋，说"我就是不喜欢 web，我就是喜欢在命令行里面，像我上课的时候就在命令行里面"，那 text UI 是什么呢？

text UI 就是：你把所有那些用于装配 UI 的 slots 全都扔掉，然后我只要有 session 和 agent，只要能在 event bus 上听到所有 session 相关的事件。

包括这种 open 的 chat completion，它还正在吐 token——我只要能看到这些，然后把它投射到我自己的命令行终端上，整个 web UI 甚至都不用动。我甚至可以做一个 web UI 的 clone、一个共享状态的 text UI。比如我现在跟它说一个"hi"，它在这运行、在输出，同时我在另外一个终端上可以看到一模一样的东西——一个非常舒服的 text UI。所以还挺好玩的。

当时在内测的时候，最早 DPC 是有 TUI 的，然后 TUI 直接被从那个 repo 里面移除了：最早官方那个 repo 里面有一个 TUI，然后 TUI 被移除了，现在有一个第三方的 text UI。

然后像 PDF reader 这种也是：它也是 hook 一些生命周期。当我看到一个东西的时候，比如加载 PDF 的时候，我就可以把我的 PDF reader 注入进去，它以这种 event 的方式来管理。而这些都还不是插件生态真正好玩的地方。

真正好玩的地方是：如果让你们来做，你们会想做什么插件呢？你们会说："这不就是一个 codex、Open Code 全部都长这样吗？我们还能干什么呢？"你能干任何事。比如如果你脑洞比较大，你就可以想象——

我们能不能把它武装成一个像 VS Code 一样的东西？那 VS Code 是什么？VS Code 的基本假设是"一个工作区就是一个目录"，然后在这个目录里面，它在左边栏有一个……

比如它可以动态地配置很多很多个小块的边栏，比如有 editor、有 browser，当然它可能也有自己的插件生态。那我们为什么不能做一个呢？这是插件内部的状态，一个插件可以维护好多 UI 的状态。

这是这个插件自己的事。然后如果我想要打开一个工作区，这不就可以吗？我可以用这种方式来管理它，也可以看——我要小一点，它还可以在底下。你想要得到 VS Code 的体验。

我可以在这里放一个 terminal，完全一样的体验。这不就是个 Cursor、就是那个 Cursor 的 agent mode 吗？它主要是一个聊天窗。而所有这一切跟插件生态、跟系统里面所有的东西都不冲突，因为它只是不断地看这个主 session。

然后它维护一些自己的状态。你看这个，我可以加 git、加 side chat，你看我还可以再加一个、再加一个 chat——这不就是 Cursor？一个开发者用许愿的方式，就可以做任何他想要做的东西。

### 8. creator mode、许愿式插件与插件语义冲突的代价

所以 DeepSeek Harness 专门给了一个——这才是释放插件生态系统、或者说一个好的架构真正能力的地方——它有一个 creator mode。

creator mode 就和比如 wake up buddy 这样的产品不一样。它说"好，我有一个预先预设的需求，那请所有人都在我的需求里面工作"。而 creator mode 给了这个 CORDIS 的权限。一般来说，你的一个 agent session 就只有 agent 的权限：比如工作区目录的读写、Bash，然后可能后面还会套一个沙箱。而在这个全火力全开的 creator mode 里，它是能看到这个世界的：它可以把插件拆了、可以往这里面加插件。也就是说，它可以在 agent 一边运行的时候，一边就往 event bus 上面挂东西。这个能力一定程度上来自于 CORDIS 的动态性——它要求一个全动态的插件生命周期，就类似于操作系统：我可以在操作系统里随时启动一个进程，也可以随时把一个进程杀掉。所以你看它像一个白板，但实际上它是一个核弹。

那为什么不许愿式插件呢？你就可以许愿插件，你就发明了 creator mode。所以你们现在有想要许个愿的吗，还是你们就回去取吧。比如我不满意——我试一下，我对现在的 UI 不太满意，能不能在 token 消耗旁边放一个超大号的？我为了快，把 F2 调成 off 了，挑一个漏，让它还是思考一下。这些都是可以用插件来实现的。Token usage，然后因为我们有所有的事件，所以它还有这种实时统计、近期推理速度。而在梁文锋时间，比我早上，推理速度还要快一点——我大概是早上、早上在外面弄一些东西的时候，就是 200 左右，现在已到 250 了。它有很好的 dashboard，如果你对这些东西不满意，你都可以去改掉、可以动态地改变这些插件的行为。

我们来看看它会做成什么样，我现在是不确定的。虽然 DeepSeek 也有这种雷霆大思考的倾向，所以我把思考调低了。呀，它开始了，我上下文有些污染，有点糟糕。然后你看到这个，这也是一个由插件管理的功能：我是立即把它放进去，还是 steer、cue message，我可以打断它，对吧。好，然后你看到我这时候需要非常危险的权限了：它需要一个 code install build，然后我就 allow——就真正的许愿式插件。那你现在就可以。

那不要了。这是许愿，因为我上课，所以就让它不要雷霆大思考、要求它快一点，因为我们完全不知道。你可以在这里面加入任何你想要的功能，相对来说不是绝对不行——绝对可以说插进去、可以真正随便组合。但这个能力对于创造者来说，它的设计理念是不一样的，更适合开发者。一会我们来看看有没有惊喜。

这个所有的好处都是有代价的。那代价是什么呢？实际上我们没有解决的是：虽然我们在 event 这一层上做了一个统一的对齐（你们都要使用同一组，然后类型匹配不匹配的，对不起，就不行），但是所有的状态管理——插件自己的状态管理——还是在自己那里，就像刚才我们说的那个 better sidebar 插件：它窗口是什么、终端怎么表示，都在自己里面。然后它有的时候当然可以自己创建一个事件推到总线上，让别人可以看到。但是插件和插件之间的语义可能是冲突的：比如我可以 hook，所以我可以实现一个上下文压缩的插件——它可以把每一次上下文。

比如输出都压缩 1/2。但如果有两个插件之间可以互相 interference——比如我加载了十个自动上下文压缩的插件，每个都压缩到 1/2，那么十的十次方就是 1/1000，那你任何输出都被压缩到没法看了，信息就全部丢掉了。也就是说，虽然它们之间可以组合，但比如它们的先后顺序——一个检查输入、一个改写输入——到底检查在前还是改写在前，其实我们没有规定。这是语义，和应用语义相关的。

essential complexity 是永远不可能解决的。插件只是说它减少了一些 accidental complexity，以及在你做一些事的时候（比如我要做这种动态 UI 生成）变得更开心了。但系统里面这些带有冲突的语义——比如两个 hook，一个要求停止、另一个要求继续，它们其实是冲突的；当 hook 运行到"停止"时，这个就被停掉了——这种语义冲突永远没有办法，在这种架构里是不解决这些问题的。你可能需要另外一个机制，比如再放一个 blackboard，然后在需要的时候它们再去共享这个状态。那这个时候抽象就有限；当你有这种需求的时候，抽象就有泄露。

### 9. 开源生态、SuperApp 接入与 dynamic UI 演示

所以插件不是万能的，架构也不是万能的。但你也可以看到，一个好的架构会给我们带来一些很有趣的启发。我们的这个……只有这个吗？只有这个吗？但它还在思考，好吧行吧，那就认为这也是一个驾驶舱吧。而真正的、我觉得真正的架构给我们带来的是什么呢？带来的是一整个软件的生态。所以说我们从需求——前面一直讲了一个简化的模型：我们做一个需求，需求确定以后就把产品 release 出去，release 出去以后它就挣钱了。但 DeepSeek Harness 走了一个不太一样的路线：它在 release 的时候 release 了一个 nothing，或者说有一些基本的东西、基础的抽象和一些第一方的东西，然后把剩下的东西交给了开源的生态。

所以你看到我们上周在北京有一个线下 meetup 活动，这完全是由开发者自己组织的，跟官方没有任何关系，没有任何 DeepSeek 的人到场；我正好因为要去北京，顺便到会场闪现了一下。而这意味着它在 DPC harness 基础上可以长出一整个生态，你想要什么就有什么。所以我自己对这个开源社区的感觉是：开发者被"带歪"了。如果是我在第一方——我在第一方 DeepSeek 发 Harness 的时候——我可能不会 Vibe 这些，这么好的东西，我不会用它来 Vibe 一个什么高达驾驶舱，我显然会 Vibe 一些更了不起的东西。

所以在我看来，这样一个 event bus 真正的能力在哪里呢？它不在于接这种 fancy 的小东西——我可以 hook 这个事件，然后把我的 UI 做一个增强——而是我可以接一整个生态。它当然可以互相增强：比如调用工具，就有很多工具可以进来，工具还可以互相组合。

我第一个想要接入的是 SuperApp。SuperApp 只需要一个非常小的抽象层，但我对 SuperApp 可能是要改造的：它首先要有 web UI，但没有 web UI 也行，我可以用一个 bridge 把它和 DPC harness 连起来。这个 SuperApp 我只需要支持两个操作：第一，SuperApp 里面总是有对象的，比如打比方 WPS，我现在在做幻灯片，那我第一个操作是可以把一些对象锁住——比如第一页、第二页，第二页你就别编辑了，我现在锁住第二页；然后我可以把这个对象 hand off，从总线上面送到模型的上下文里；第三，我可以把修改的对象从模型的上下文里拿回来，替换回我的 SuperApp 里。我只需要对 WPS Office 做一个这样的最小改造。

我就给一个超级应用赋予了 AI 原生的能力，而且它可以享受到 DeepSeek Harness 插件生态里面所有东西的好处——这是一个非常恐怖的能力。DSH 是一个非常小、非常薄、什么也没有的内核层，但它底下有一整个大的插件生态，这是 AI 的生态。同时我的任何一个 SuperApp 都可以做到这一点。我今天花 5 分钟 Vibe 了一个——当然没有 Vibe WPS，我做了这样的一个东西——但这个 demo 就可以告诉你，任何 SuperApp 在上面都是可以的。大家用过 Excel 吗？你可以用它来拖东西、可以拖各种东西、可以 hello，OK，这就是一个 super WPS，任何能嵌在网页里的都可以。

我做了一个 bridge。我可以干一件什么事呢？AI 可以指定一下这个 turtle，在框里画一个 turtle 用的元素，有一些文本标签，在这个时候 AI 就开始工作了。所有的编辑你看都是可以照常进行的，但这个对象被锁住了。所以我的接口只要对于这个 SuperApp——我只需要把一些对象锁住，然后把锁住的对象 hand off 给模型，模型再回来。注意，因为我是放到这个总线上的，整个生态都归我。然后有了：一个没有任何 AI 能力的 application，可以以任何方式把它的任何对象以最合适的形式接入 AI。

这是什么？你就想想 WPS：你用 Kimi 让它做一个 PPT，做了 PPT 以后，他自己那个产品团队再做一个 PPT 的 editor，然后你可以拖那个框、可以加 comment、加一个注释，不满意再让他改。但你为什么不反过来做这件事？这是一个生态、真正的 AI native 的东西。你看第一方，所有东西都可以编辑——它是 Excel 的 door，这个你不满意还可以再改，这个龟壳你不满意还可以把它删掉，做得不错。这是 DeepSeek 的 flash 版本。

这是一个。然后你的空间就大了，你可以做一个 Blender 的 bridge。这就是为什么 MCP 只要做一个非常小的 protocol，然后这个 protocol 甚至可以成为 DeepSeek Harness 的一个原生插件，专门做这个对象的 bridge。然后你甚至可以切换到那个聊天——当然我这个因为就花了 5 分钟来 Vibe，做得比较简单，就是一个这样的 AI 聊天框——完全可以把它和 bridge 连起来。我可以回到这里来编辑它，这个画 turtle 的 session 还在，然后这个高达驾驶舱依然还能生效。这是第一个大型 app 的 AI 增强。

然后第二个方向：因为我们的 event bus 特性可以随便 hook，所以其实我们可以建立一个 session 和模型的双向通道。我们只要允许模型输出一个 HTML 加 JS 的卡片，我就可以把这个卡片放到界面的任何 slot 上。这个能力在哪里呢？我可以生成一个卡片，注意这个卡片是有 JS 的，而 JS 意味着我这里可以放一个按钮、可以放一个输入框、可以放任何东西，我甚至可以放一个 Excel editor、放一个 WPS。理论上说我可以写一个 React component，就是一个非常复杂的东西，就放在这。然后放在这以后，我允许某一些 JS 调用往 event bus 上面注入一个事件，我就可以把东西注入到模型的上下文里。我可以把一个动态的 UI 生成出来，并且可以把 UI 里面的点击、鼠标的点击事件以及里面的状态，通过一段 JavaScript 重新注回上下文里，然后这个上下文完了以后，它又可以再指导这个 UI 的更新。这不就是一个 generative UI 的应用吗？所以我也做了，虽然这也是 5 分钟。这里面还有很多细节：我只要和它做好一组约定，比如约定这个 DIV、一个叫 DSH dynamic UI 的 div，只要碰到这样的 DIV 在输出里，我就完全是许愿似的，就跟插件说"我要做这个事"，然后它碰到这个就会以一个卡片的方式来呈现。

等我稍微缩小一点，就能看到全部了，然后它会生成一段带 JavaScript 的代码。当然我现在所有代码每次都是重新生成的，所以长度会比较长；但你总是可以设计 DSH、设计一个好的方式去复用已有的东西，这样就可以把它做得更短。比如我现在可以跟 AI 玩成语接龙：找一个比如以"惊弓之鸟"开局，你可以看它对话的过程——相当于我点击了这个按钮以后，这个 JavaScript 会往模型的上下文里面注入这样一句话（就是字符串拼接的，只要是可以代码做的），然后模型就会开始输出，它接"鸟语花香"，接完以后可以生成一个对界面的 patch。虽然我现在生成的不是截图，而是直接再生成一个新的卡片。

好，有些 bug 不要紧，因为我关闭了思考。这个状态是带着的，带着"鸟语花香"，它不思考，确实还是有些问题。就是完全 Vibe，然后如果你想要额外的、想要外挂任何东西，就做一个五子棋，要求五子棋的状态在 UI 里，但是所有下棋落子都是模型思考以后做的。我为了让它能快——鸟语花香、香火不绝、绝处逢生——那我再来一个。配合它的好处是什么呢？我可以配合一系列和 dynamic UI 相关的插件：比如怎么样做上下文的压缩、怎么样做上下文的管理，甚至上下文的 fork；以及这个插件生态一方面可以更好地让我和这个 UI 交互、省下上下文，另一方面我甚至可以把整个 session、不要这个聊天框，可以面对我的一个任务，生成一个真正好的 generative UI。

来我们看看，这次它可以了，虽然有点 bug——五子棋是下在线上来了——但我们试一下。它开了 DeepSeek 的思考，这肯定不是一个成熟的产品。但你们回想一下，到 ChatGPT 的时刻、GPT-3.5 的时候，我记得我就算让它输出一个"从 50 数到 100"，它都"五十五十一、五十一五十一"，然后你肯定会觉得这个东西现在又慢又不好用。但当你看到一种可能性、它能做到一点的时候，就意味着一定有办法可以做得非常非常非常好。所以这就是架构。你看它在这里下了一个、在这里下了一个。所以到这里，在创造模式下，这个东西能做出什么完全取决于你的想象力——你就是在许愿式地做这件事。

### 10. 插件实现原理、开发者生态与操作系统式闭环展望

那我们也可以了解一下：不要再做，你能看一下插件实现到底是怎么注入管理员、到底有多少入侵、有没有改掉。你可以深入到这个架构：可以先许愿达到你的预期效果，然后再让它告诉你这是怎么办到的。然后我们再来开一个 coding agent，这也是完全我许愿就一把出的。你别说，你很好奇一整个应用和它和 DSH 之间是如何通信的。你现在需要的就是一种相信——相信这件事情从 first principle 上是做得到的，然后你就大胆地让模型去做。它是一个 Cordis 插件，被 DSH 放到宿主进程；工具调用不直接改画布。

只是暂存 store，点 begin 生成一个 job，把选区 id 锁在画布上。OK，这相当于一个非常薄的应用改造层：因为要支持对对象的选择和锁定，然后把它们挂到里面，把应用做成 agent 宿主插件。画布等于 session，编辑请求等于 tool call，提交等于回合结束的 commit，完全没有入侵其他的。

能和其他插件的能力组合吗？上下文注入——给模型的上下文注入，这个有意思。因为动态 UI 我做了这个 web 插件以后，我需要给每一个 session 注入提示词：因为你看我的插件使用是有条件的，我需要它生成一个带特别标记的 div。相当于我是一个 DSL，你可以理解成我可以做一个 DSL，这个 DSL 可以生成一个 div，然后我必须要让模型知道要生成这样的 div，才能变出一个正确的动态 UI 插件，所以我首先要给模型注入上下文。

你看这就是 CORDIS、整个生态设计的——不是 CORDIS，是加上 DPC harness 的核心层设计——它只要一个 context.system prompt 的事件。你看在这里插入一段 1.5KB 的协议，说明它会勾住这个 event。然后这是插件唯一写进模型上下文的东西，然后模型的输出到 UI 状态，提取不新增消息的类型，靠标记加投影、event sourcing——完全是事实。

就是我可以根据事实的历史来读到这里面是不是有——我插件可以检查。同样是 event，当一个模型的输出结束以后，我可以知道里面有没有；有的话它就可以改变我自己的状态。比如 UI，我不知道它是怎么实现的：它可以是在往一个 slot 里面去插入这个界面，或者 whatsoever。但这显然也不会入侵到整个系统实现的部分。它有一些 CORDIS 服务的依赖，然后一些 session projection 的回调、system prompt——这个有点入侵：它加了一些自己的 library、浏览器 remote session、prompt、打包 profile，然后完全没有动底层的架构，只靠这个系统的架构。

然后还有这个也是类似的，我们看一下，没有侵入。而且 DeepSeek 通过 scope 机制在机制上限限制了：我的插件如果想要干一些坏事——它匹配不上它所声称的东西的时候，就会自动 fail，相当于是隔离了。同样它也就是只注册了一些事件：比如对这个全局事件 assistant stream 旁听，而且它只做了一个对象同一性过滤（别人的 agent 它不匹配）。它说在后台启动一个 inference session，然后只是从 inference session 里面拿一个结果，到这个 Excalidraw 的画布里面来。当然现在没有刻意的组合，是因为我完全是许愿。
